# `@ergots/ergoscript` — Wire Format Contract

This file documents the **wire-format slice** of the `@ergots/ergoscript` boundary contract. For cross-cutting guarantees (browser-compat, determinism, ESM-only, no-WASM, runtime deps) and forward pointers to other slices, see [`facts/ergoscript.md`](./ergoscript.md). For the evaluator surface (which consumes the `SValue` / `SType` / `Expr` types this layer produces) see [`facts/ergoscript-eval.md`](./ergoscript-eval.md). For sigma-protocol verification see [`facts/ergoscript-sigma.md`](./ergoscript-sigma.md).

Authoritative wire-format reference: sigma-rust's `ergotree-ir/src/ergo_tree.rs`, `ergotree-ir/src/serialization/`, and `ergotree-ir/src/mir/` (branch `integration/ergots`, HEAD `ed5452cf`). Where this file is silent, those are canonical. Where ergots and sigma-rust diverge, the JVM `sigma-state` reference is canonical (the divergences are called out in place).

## Scope

The wire-format slice provides:

1. Parse + serialize for the ErgoTree envelope: header byte, optional VLQ-u32 body size, optional segregated constants section, body Expr.
2. Parse + serialize for the full `Expr` discriminated union (69 variants — see `mir/types.ts`, including the bare `0xa6` op-form `LastBlockUtxoRootHash`), wired through a central opcode-dispatch switch.
3. Parse + serialize for `SType` (the type-system union) and `SValue` (the runtime-value union), including all primitive variants, `SColl`, `STuple`, `SOption`, `SFunc`, `STypeVar`.
4. Parse for `SigmaBoolean` (the recursive proposition tree inside `SSigmaProp` constants) as a structural 6-variant discriminated union — see [`facts/ergoscript-sigma.md`](./ergoscript-sigma.md) for the runtime type and verifier; the wire parser produces all 6 variants byte-equal on round-trip.
5. P2PK recognition + 33-byte public-key extraction.
6. Base58check address ↔ `ErgoTree` round-trip for mainnet and testnet (P2PK and P2S).
7. Stateless: no I/O, no clock, no PRNG, no `globalThis` reads. (Cross-cutting browser/determinism guarantees: see the meta file.)

## Public surface

### Primary exports

```ts

// A box's tree under the box rules, and the bytes the JVM writes for it (see "Box trees" below)

```

### `parseTree(bytes, opts?)`

- **Precondition:** `bytes.length >= 1` and `bytes.length <= MAX_TREE_SIZE` (1 MB). The cap mirrors sigma-rust's practical bound (largest real-world ErgoTree in the PR 862 corpus is ergoraffle at 931 bytes); 1 MB is comfortably above that ceiling while bounding memory against adversarial inputs. The JVM has no such cap (residual 6).
- **Options:** `opts.checkType` (default `false`) applies rule 1001, the root-type check (see "Rule 1001 on the box paths" below). The default is lenient, the JVM's `checkType = false`, because the ErgoTree wire kind and the eval vectors parse arbitrary-root trees with it; the box paths pass `true`.
- **Parse:** `parseTreeFromReader` over the bytes (see its paragraph below). The tree is read under its 4096-byte window, as the JVM's lenient parse is, so a read that begins past the window degrades a size-flagged tree and rejects an unsized one. The exception is a value read (a value's first byte, or Relation2's lookahead) at the very end of the input: its unchecked peek fails first, a hard `ReaderError('truncated')` whatever the size flag (see "Value read order").
- **Postcondition (success):** Returns an `ErgoTree`; for a canonically encoded tree, `serializeTree` of it is byte-identical to the input (see `Round-trip invariant` and its carve-outs). Bytes left after the parse end are tolerated only while they lie within a size-flagged tree's declared span (`bodyPos + declared`, where the retired bounded sub-reader ended), so `09 03 08 d3 00` parses; a byte beyond that span, or any byte after an unsized tree, throws `'trailing-bytes'` (ERG-02; residual 6).
- **Postcondition (failure):** `ErgoTreeParseError` for the envelope (`'empty'`, `'oversized'`, `'trailing-bytes'`) and for the tree parse (`'header-version-requires-size'`, `'body-size-overflow'`, `'too-many-constants'`, `'soft-fork-without-size-bit'`, `'nested-tree-truncated'`). The tree parse wraps two failures, each with the original error as `cause`: a soft-forkable failure in a tree without the size flag surfaces as `'soft-fork-without-size-bit'` (so a caller of `parseTree` on such a tree gets the wrapper, not, e.g., `ExprParseError('opcode-reserved')`), and a nested tree's run-out, a `'truncated'` raised in a nested tree's constants or body or a nested tree's degrade span that runs past the end of the input, surfaces as `'nested-tree-truncated'` (a nested tree reads its header and size before its `try`, so a run-out there reaches the enclosing tree unmarked; see `parseTreeFromReader`, step 2). Every other failure surfaces unwrapped from the innermost layer that rejected the bytes: `ExprParseError` from the body parser; `STypeParseError` / `SValueParseError` / `SigmaBooleanParseError`; `ExprTpeError` from rule 1001's root type (with `checkType` only); and `ReaderError` from the cursor (`'truncated'`, including a value's first-byte peek at the end of the input, `'vlq-overflow'` and `'max-tree-depth-exceeded'`). A window error inside the tree (`'position-limit-exceeded'`, rule 1014: a checked read that begins past the tree's own window, or past a Box constant's candidate window) is in the degrade set, so it never surfaces on its own: a sized tree degrades, and an unsized one throws the wrapper. A value read at the very end of the input fails its unchecked peek first instead, with a hard `'truncated'`.

### `serializeTree(tree)`

- **Precondition:** `tree` was either returned from `parseTree` or constructed satisfying the type invariants below. Bits 0–4 of `header.rawHeader` (version, size flag, segregation flag) MUST match `header.version`, `header.hasSize` and `header.constantSegregation` (checked at serialize time); bits 5–7 are free. `constantTypes.length === constants.length` is required.
- **Postcondition:** An `UnparsedErgoTree` returns its bytes verbatim. A parsed tree is written from its structure, as the JVM's `serializeErgoTree` writes it (`ErgoTreeSerializer.scala:79-127`): `rawHeader` as stored (the JVM writes `ergoTree.header` and never inspects bits 5–7), then, for a size-flagged tree, the size recomputed from the constants and body actually written, then the constants and the body, each node through the serializer its JVM `companion` picks, which can differ from the opcode it was read with (Round-trip Carve-out 8: a Boolean-constant collection read as `0x83` is written `0x85`, a method call without arguments read as `0xdc` is written `0xdb`). The JVM's pre-v3 builder also rewrites arithmetic operands at parse and at write, which ergots does not model (residual 11). Returns `Uint8Array` of length ≤ `MAX_TREE_SIZE`. For a canonically encoded `b` accepted by `parseTree` (encoded as the JVM writes it), `serializeTree(parseTree(b))` equals `b` byte-for-byte, except for the shapes that parse but cannot be written (Round-trip Carve-outs 1, 5, 6, 7 and 9, and Carve-out 8's non-Boolean item), where it throws; a declared size that differs from the body is not canonical (Round-trip Carve-out 4).
- **Postcondition (failure):** Throws `ErgoTreeSerializeError` with `code` `'header-inconsistent'` (bits 0–4 of `rawHeader` disagree with the derived fields), `'constants-arity-mismatch'`, `'oversized'` (serialized bytes would exceed `MAX_TREE_SIZE`), or `'too-many-constants'` (`tree.constants.length` > 100000, the parse bound, so no tree it writes carries a constants count the parse refuses; ERG-05. A tree it writes can still fail to re-parse on the 4096-byte window, which the parse applies and the serializer, like the JVM's, does not). Body-serialize failures surface as `ExprSerializeError` (notably `'not-supported'` for the un-encodable `ZkProofBlock` variant, `'func-value-arg-id-out-of-range'` / `'val-use-id-out-of-range'` for a FuncValue argument id or ValUse id outside [0, 2^31), Round-trip Carve-out 5, and `'collection-item-not-boolean-constant'` for a Boolean-constant collection holding a constant of another type, Carve-out 8) or as `SValueSerializeError` (`'savltree-key-length-out-of-range'` / `'savltree-value-length-out-of-range'` for an SAvlTree constant's `keyLength` or `valueLengthOpt` outside [0, 2^31), Round-trip Carve-out 6, and `'sbox-index-out-of-range'` for a Box constant whose index is 0x8000 or more, Carve-out 9) or as `STypeSerializeError` (`'tuple-too-short'` for an arity-0/1 tuple type, Round-trip Carve-out 1, and `'stypevar-name-length'` for an `STypeVar` name whose re-encoding exceeds 255 bytes, Carve-out 7); a hand-built SigmaProp constant can also raise `SigmaBooleanSerializeError`.

### ErgoBox sub-structure readers (`parseErgoTreeBytes` / `parseAdditionalRegisters`)

Reader-based readers factored out of the `SBox` data parser (`parse-svalue.ts`, `case 'SBox'`) and forwarded top-level from the package index so `@ergots/transaction`'s ErgoBoxCandidate codec consumes the box-body grammar from ONE place rather than re-deriving the ergoTree-length / register-section layout. Both operate on a shared `ByteReader` and advance the cursor in place.

```ts
parseErgoTreeBytes(r: ByteReader): Uint8Array
parseAdditionalRegisters(r: ByteReader, treeVersion: number): AdditionalRegisters
type AdditionalRegisters = Record<number, { tpe: SType; value: SValue; opaqueBytes?: Uint8Array } | undefined>
```

- **`parseErgoTreeBytes(r)`** — consumes one ergoTree under the box rules and returns its span `[start, end)` as a DETACHED `Uint8Array`: `parseTreeFromReader(r, { checkType: true })`, the JVM box parser's call (`ErgoBoxCandidate.scala:194`, `checkType = true`). The span is raw and keeps the declared size as received: a box's R1 and `propositionBytes` are these bytes, as the JVM's `ErgoTree.bytes` is the parser's retained `propositionBytes` (`ErgoTree.scala:123-131`; `ErgoTreeSerializer.scala:179-181`). `end` is where the JVM continues reading the box: the parse end for a tree that parses, whatever its declared size says, and `bodyPos + declared` for a tree that degrades. It seeds the box-tree cache with the tree it parsed, keyed by the returned span (see "Box trees" below), so `boxTreeOf` / `reencodeTreeBytes` on those bytes reuse this parse. Does NOT enforce outer-trailing exhaustion (the caller continues with the next field, e.g. `creation_height`). Failure surface: every error of `parseTreeFromReader` (see its paragraph) — `ErgoTreeParseError` (`'header-version-requires-size'` from the tree's own header, `'body-size-overflow'`, `'too-many-constants'`, `'soft-fork-without-size-bit'`, which is how an unsized tree with a non-SigmaProp root rejects, and `'nested-tree-truncated'`), `ExprTpeError` from rule 1001's root type, and the body's wire parse errors (`ExprParseError` / `STypeParseError` / `SValueParseError` / `SigmaBooleanParseError` / `ReaderError`). **The `SBox` data parser and `@ergots/transaction`'s ErgoBoxCandidate codec both call this**, so both apply the same box rules. The bare `parseTree` is lenient by default (no rule 1001): the JVM's `private[sigma]` `checkType = false` form, which SANTA's blesser uses for the ErgoTree wire kind. `parseTree(bytes, { checkType: true })` is the JVM's `ErgoTree.fromBytes`. Apart from `parseTree`'s envelope checks, that option is the only difference between the box path's tree parse and the bare one.
- **`parseAdditionalRegisters(r, treeVersion)`** — reads the box additional-registers section in the JVM candidate parser's order (`ErgoBoxCandidate.scala:226-234`): a raw `u8` count (`getUByte`, NOT VLQ), then, for each register in turn, keyed R4.. (`4 + i`): (1) the register id is resolved first, so a seventh register rejects with `SValueParseError('sbox-registers-out-of-range')` only when the loop reaches it, after R4–R9 have been read (the JVM's `nonMandatoryRegisters(iReg)` index error, `:230`); (2) the value is read whole (the JVM's `r.getValue()`, `:231`, in the value read order below); (3) rule-1019 `CheckV6Type` runs once on the complete value (`:232`; `'register-v6-type'`). So a hard error in the value's data comes first — SHeader data in a pre-v3 tree (`'sheader-tree-version-too-low'`, `CoreDataSerializer.scala:144-146`) or an UnsignedBigInt longer than 32 bytes (`:118-124`) — and a Tuple register is checked only after all its items are read and its level lowered (`ValueSerializer.scala:409`); checking each item as it is read would let an early item's rule-1019 failure degrade a tree the JVM rejects on a later item's hard error, and would leak one level more. Inside a sized tree (a nested Box's registers) `'register-v6-type'` is in the degrade set. Each register is restricted to `Const`/`Tuple` (residual 4); the rare Tuple-Expr form (lead byte `0x86`) is preserved via `opaqueBytes` for byte-identical re-emission. A register value, or a register Tuple's item, led by any other byte is classified as the JVM's `r.getValue()` classifies its first byte (2026-09-29): an opcode with no JVM serializer throws `parseExpr`'s soft `'opcode-reserved'` / `'unknown-opcode'` (rule 1002 `CheckValidOpCode`, `ValueSerializer.scala:171-175`), which degrades an enclosing sized tree and, outside any tree or in an unsized one, rejects; a known opcode, and each of the six opcodes of residual 5, throws the hard `SValueParseError('sbox-register-unsupported-expr')` without its payload being read (the JVM's register cast rejects most such nodes, `ErgoBoxCandidate.scala:231`; residual 4 has the exceptions). The caller owns any surrounding read-window (`positionLimit`) save/restore. **The `SBox` data parser calls this** for its registers, so register semantics are identical across SBox and the candidate codec.

### Shared rules for `@ergots/transaction` (`violatesCheckV6Type` / `sValueStructuralEq`)

Two pure functions forwarded top-level so that `@ergots/transaction` applies the JVM's rules from the same code as ergoscript does, rather than re-deriving them.

```ts
violatesCheckV6Type(tpe: SType): boolean
sValueStructuralEq(a: SValue, b: SValue): boolean
```

- **`violatesCheckV6Type(tpe)`** — rule-1019 `CheckV6Type` (JVM `ValidationRules.scala:165-205`): true iff `tpe` contains `SOption`, `SHeader` or `SUnsignedBigInt`, recursing through `STuple` items and `SColl` element types. The JVM applies it to box registers (`ErgoBoxCandidate.scala:232`) and to context-extension values (`ContextExtension.scala:62`). The register leg is `parseAdditionalRegisters` (`'register-v6-type'`); the extension leg is `@ergots/transaction`'s `parseContextExtension` (`TxParseError('extension-v6-type')`).
- **`sValueStructuralEq(a, b)`** — the JVM's uncosted data equality (Scala `==` on data values, which `ConstantNode.equals` applies through `Objects.deepEquals`). A Box compares by its id over its retained bytes (`CBox.equals`), a GroupElement by its point, a SigmaProp structurally, an AvlTree field by field (flags byte unmasked, see `facts/transaction.md` Known residual 3). It does not compare types: callers comparing constants check the types separately. It is the uncosted form of the evaluator's `Eq`/`NEq` comparison, which differs only in throwing, as the JVM's costed comparer does, on a SigmaProp conjecture compared with a node of another kind; `startsWith`/`endsWith` use it too. `@ergots/transaction` uses it for storage-rent register equality.

### Box trees (`boxTreeOf` / `reencodeTreeBytes` / `seedBoxTree`) and box bytes (`boxBytesOf` / `boxIdOf`)

The JVM keeps a box's tree bytes as received for `propositionBytes` and R1, and re-encodes the tree from its parsed structure wherever it re-serializes the box (spec `docs/specs/2026-09-28-sized-tree-declared-size-design.md` §§8–10). ergots' box types carry only the bytes (`ergoTreeBytes`), so the parsed tree lives in a cache beside them (approach B: a cached helper, no change to the box types).

```ts
boxTreeOf(ergoTreeBytes: Uint8Array): ErgoTree
reencodeTreeBytes(ergoTreeBytes: Uint8Array): Uint8Array
seedBoxTree(ergoTreeBytes: Uint8Array, tree: ErgoTree): void
boxBytesOf(box: ErgoBox): Uint8Array
boxIdOf(box: ErgoBox): Uint8Array
```

- **`boxTreeOf(ergoTreeBytes)`** returns the box's tree under the box rules. It reads a `WeakMap` keyed by the `Uint8Array` **instance**, which `parseErgoTreeBytes` seeds with the tree it parsed, so a parsed box is not parsed twice and a spend reuses the ingest parse. On a miss — bytes that did not come through box ingest, such as a hand-built `ErgoBox`'s, or a copy of ingested bytes — it parses the bytes once, standalone, with `checkType: true`, and caches the tree it gets (a failure is not cached, so the next call parses again). The result is the cached tree object itself, shared by every caller (a spend evaluates it), which callers must not mutate. The miss rule:
  - **The tree's own reads run out of input** (`ReaderError('truncated')` not marked as a nested tree's: including from a first-byte peek or the size read, and from a nested tree's header or size read, which come before that tree's `try`): a size-flagged tree becomes an `UnparsedErgoTree` over the raw bytes when the bytes are its declared span. Box ingest keeps a parsed tree's whole body in its span, so such bytes are the declared span of a tree that, in its box, degraded after its reads went past that span: exactly `bodyPos + declared` bytes, in the JVM's Int arithmetic (`ErgoTreeSerializer.scala:200`). Bytes of any other length cannot be that span, so for them the run-out propagates (2026-09-29; `09 05 d1`, a declared size of 5 over 3 bytes, throws `'truncated'`). A span can end inside the size VLQ, from a declared size that is negative as an Int (2026-09-29, final fix round 2): `numBytes = 1 + L + toInt(v)`, with `L` the size VLQ's length on the wire. The JVM reads the size with `getULong` under `getUInt` (scorex-util 0.2.1 `VLQReader.scala:54-58, 75-89`): at most 10 bytes, a value of at most 2^32 − 1, at least 5 groups for a value of 2^31 or more, zero groups after those (a tenth counts only its low bit, which must be clear), and the size's last byte never inside such a span. So bytes of length `n` whose size read runs out are a span iff some `L` in [max(`n`, 5), 10] writes `v = 2^32 + (n − 1 − L)` with the bytes after the header as its first `n − 1` bytes: `09 fe ff ff` (`L` = 5) and `09 fc ff ff ff` (`L` = 8, an over-long size) are spans, as is `09` alone (`L` = 5 to 10), while `09 fe`, `09 80` and `09 ff ff` are not, and their run-out propagates. A sigma-state 6.0.6 probe kept all 45 such spans (every `n` and `L`). A span of the header alone can reach no box: the box parse continues after it, reads the rest of the size as the creation height, and rejects it as above `Int.MaxValue` (`getUIntExact`). For a tree without the size flag the error propagates. An empty array has no header byte and reads as a tree without the size flag, so a miss on it throws `'truncated'`; box ingest can yield an empty span (a declared size that wraps negative so the degrade's `numBytes` is 0, as in `09 fa ff ff ff 0f …`), and its seed re-encodes it to an empty array.
  - **A nested tree runs out of input** (`'nested-tree-truncated'`): its constants or body reads, or its degrade span, run past the end of the bytes (its header and size reads count as the enclosing tree's, above). The result is ambiguous: in the box, the bytes after this tree may have held them — a nested tree may have degraded after reading past this tree's end and moved back, leaving this tree parsed, or degraded over a span that ends past this tree's end before this tree itself degraded. The miss throws `ErgoTreeParseError('box-context-required')` with the marker as `cause`; a JVM-faithful result for such bytes needs the ingest seed or `seedBoxTree`. The rule is conservative, a safe direction: some of these outcomes are decidable from the bytes alone, and the miss still refuses them. For example, an enclosing tree without the size flag cannot have degraded, so if its bytes came from box ingest, a nested run-out means the nested tree degraded to its declared span and this tree parsed; the miss throws rather than reconstruct that.
  - **Any other failure propagates.** It does not depend on the bytes after the tree: such bytes are not a valid box tree, and the JVM's `ErgoTree.fromBytes` (`ErgoTree.scala:413-415`, `checkType = true`) would throw too.
  - **Trailing bytes** after the parse end throw `ErgoTreeParseError('trailing-bytes')`: leaving them in place would make R1 (the raw bytes) and the re-encoding disagree.
- **`reencodeTreeBytes(ergoTreeBytes)`** is `serializeTree(boxTreeOf(ergoTreeBytes))`, cached on the same entry: the bytes the JVM's candidate serializer writes (`ErgoBoxCandidate.scala:142` → `serializeErgoTree`, `ErgoTreeSerializer.scala:105-127`). A parsed tree re-encodes from its structure, with its header byte as stored and, when size-flagged, its true size; an `UnparsedErgoTree` re-encodes to its raw bytes, as the JVM returns an `UnparsedErgoTree`'s bytes. It throws what `boxTreeOf` throws on a miss, and what `serializeTree` throws; only a success is cached, so a tree that cannot be re-encoded (Round-trip Carve-outs 1, 5, 6, 7 and 9, and Carve-out 8's non-Boolean item) throws on every call. The result is the cached array (for an unparsed tree, the tree's own bytes), which callers must not mutate.
- **`seedBoxTree(ergoTreeBytes, tree)`** attaches a tree an embedder parsed itself to those bytes, as a JVM box built from an `ErgoTree` object carries its tree. ergots' SANTA eval harness uses it for its synthesized SELF, which the blesser builds from a leniently parsed tree.
- **Cache rules.** The rule from `eval/_box-id.ts` applies: the bytes must not be mutated after first use, or the cache goes stale. The key is the instance, so a copy of seeded bytes is a miss. The cache belongs to one module instance: if the package is loaded twice, each copy fills its own.
- **Copying `ergoTreeBytes`.** Code that copies a box's `ergoTreeBytes` must keep the ingested instance, or seed the copy with the original's tree: `seedBoxTree(copy, boxTreeOf(original))`. An object spread keeps the reference, and with it the entry; `slice()`, `Uint8Array.from`, a hex round-trip or a structured clone makes a new instance, which misses. A miss re-parses the span to a tree equal to the ingest's (an unparsed one may carry another diagnostic `error`), except for the two spans a standalone parse cannot reproduce: an empty span, where the miss throws `'truncated'`, and a span in which a nested tree read, or degraded, past the span's end, where it throws `'box-context-required'` (see the miss rule above).
- **Write sites.** `writeBoxBodyWithoutRef` writes `reencodeTreeBytes(box.ergoTreeBytes)`, so every box serialization here emits the re-encoded tree, as the JVM's does: `serializeSValue(SBox)` (the Box vector, and Box constants inside a tree, as in the JVM's `DataSerializer`), `serializeBoxBytes` (the fallback of `boxBytesOf` for a constructed box, and so its id), and `serializeBoxBytesWithoutRef` (`bytesWithoutRef`). The evaluator's `serialize` cost of a Box charges the re-encoded length ([`facts/ergoscript-eval.md`](./ergoscript-eval.md)); `@ergots/transaction`'s candidate serializer writes the re-encoded tree too ([`facts/transaction.md`](./transaction.md)).
- **Kept as received.** `ergoTreeBytes` stays raw wherever the JVM keeps the bytes: R1, `propositionBytes` and `ExtractScriptBytes`, and a parsed box's `retainedBytes`.
- **`boxBytesOf(box)` / `boxIdOf(box)`** (`eval/_box-id.ts`, root-exported since 2026-09-28) are the JVM's `ErgoBox.bytes` and `ErgoBox.id` (`ErgoBox.scala:87-92`): the slice the box parser retained, as received, for a box that came off the wire (`ErgoBox.scala:214-226`), else `serializeBoxBytes(box)`, which writes the re-encoded tree. The id is `blake2b256` over those bytes, memoized per box object. `@ergots/transaction` uses them for its input and data-input id checks and for the storage-rent fee.

### `isP2PK(tree)` / `p2pkPublicKey(tree)`

- **Precondition:** `tree` is a valid `ErgoTree`.
- **Postcondition (`isP2PK`):** Returns `true` iff the tree's body is the canonical P2PK shape — `Const(SSigmaProp, ProveDlog(EcPoint))` or a `ConstPlaceholder` resolving to the same — matching sigma-rust's `Address::P2Pk.script()` recognition (`ergotree-ir/src/chain/address.rs:206-218`).
- **Postcondition (`p2pkPublicKey`):** Returns a defensive 33-byte copy of the compressed secp256k1 public key when `isP2PK(tree)` is true, else `null`. The returned buffer is fresh — mutating it does not affect the tree's internal storage.
- **Invariant:** Trees whose body is `CreateProveDlog(GroupElement)` (a derived form) are NOT classified as P2PK — sigma-rust only recognizes the canonical `Const(SSigmaProp, _)` form. Using a non-canonical shape would break the address → tree → address round-trip against any other Ergo implementation.

### `addressFromErgoTree(tree, network)` / `ergoTreeFromAddress(address)`

- **Precondition (`addressFromErgoTree`):** `tree` is a valid `ErgoTree`; `network` is `'mainnet'` or `'testnet'`.
- **Postcondition (`addressFromErgoTree`):** Returns a base58check Ergo address. If `isP2PK(tree)`, the address is P2PK (content bytes are the 33-byte EcPoint only, NOT the serialized tree). Otherwise the address is P2S (content bytes are the full serialized ErgoTree).
- **Postcondition (`addressFromErgoTree` failure):** Throws `AddressDecodeError('unknown-network')` if `network` is any value other than `'mainnet'`/`'testnet'` (a runtime guard for untyped / `as any` callers that bypass the `Network` literal type).
- **Precondition (`ergoTreeFromAddress`):** `address` is a base58check Ergo address with valid checksum and a supported address type.
- **Postcondition (`ergoTreeFromAddress`):** Returns the `ErgoTree` encoded by the address. P2PK addresses are reconstructed by synthesizing canonical bytes (`0x00 0x08 0xcd <33 bytes pubkey>`) and parsing them — every returned tree goes through `parseTree`, so the type invariants below hold. A P2S address's content bytes parse under the box rules, `parseTree(bytes, { checkType: true })`, as the JVM's decoder calls the one-argument `deserializeErgoTree` (`ErgoAddress.scala:322` → `ErgoTreeSerializer.scala:132-139`, `checkType = true`): a root that fails rule 1001 rejects a tree without the size flag (`'soft-fork-without-size-bit'`) and degrades a sized one, so a P2S address can decode to an `UnparsedErgoTree`.
- **Postcondition (failure):** Throws `AddressDecodeError` with `code` `'bad-base58'`, `'too-short'`, `'too-long'` (address string longer than `MAX_ADDRESS_STRING_LENGTH`, bounding the O(n²) base58 decoder), `'checksum-mismatch'`, `'invalid-p2pk-length'`, `'p2sh-unsupported'`, or `'unknown-type'`. A P2S address carrying malformed tree bytes throws what `parseTree` throws (see its postcondition), unwrapped by the address layer.
- **Round-trip invariant:** For any tree `t` that passes rule 1001 and whose re-parse stays inside the 4096-byte window, and matching network `n`, `ergoTreeFromAddress(addressFromErgoTree(t, n))` parses to a structurally equivalent `ErgoTree`. The address length cap admits trees up to `MAX_TREE_SIZE` (1 MiB), but decoding parses them under the window, where a read that begins past it degrades a sized tree and rejects an unsized one (see `parseTree`). P2SH addresses are NOT round-trippable through this function (they are derived from a 24-byte hash, not a serialized tree) and decoding one throws `p2sh-unsupported`.

`parseExpr` accepts the parallel-indexed segregated constant arrays from the surrounding ErgoTree envelope. `constantTypes` is consulted by the `ConstantPlaceholder` handler to recover a placeholder's `SType` from its id; `constantValues` is reserved for substitution-at-parse-time semantics (sigma-rust's `substitute_placeholders` flag — not currently used). `valDefTypes` is a shared scope-wide `Map<ValId, SType>` populated by `ValDef` parsers and read by `ValUse` parsers (mirrors sigma-rust's `SigmaByteReader.val_def_type_store`); the outer envelope creates a fresh empty map per tree, and recursive descent shares it across the whole Expr graph. The JVM instead keeps one store per reader, shared by every tree that reader parses (residual 10).

**`treeVersion` threading.** `parseSValue` / `serializeSValue` carry a `treeVersion: number`, threaded through every recursive call site (Coll, Tuple, Option arms) — it drives the V3-gated value codecs (SHeader, SOption, SUnsignedBigInt). The internal `parseExpr` / `serializeExpr` entry points accept `treeVersion` as a **required** parameter; the optional-defaulted-to-0 form was a threading-class landmine — compound nodes silently parsed nested constants at v0. `parseTree` / `serializeTree` inject `treeVersion` from `tree.header.version`. `SHeader` value parse/serialize delegate to `@ergots/scorex`'s `parseHeader` / `serializeHeader`.

**`parseTreeFromReader(r, opts?)` (2026-09-28).** Mirrors the JVM's `ErgoTreeSerializer.deserializeErgoTree` (sigma-state v6.0.6 `ErgoTreeSerializer.scala:141-215`): the tree is parsed on the reader it arrives on — no sub-reader, whatever the size flag says — in five steps.
1. **The window** (`:142-144`). It notes `start = r.position`, saves `r.positionLimit` and sets `r.positionLimit = start + MAX_PROPOSITION_SIZE` (4096, `SigmaConstants.MaxPropositionBytes`, `core/.../sigma/data/SigmaConstants.scala:40`; every JVM caller passes it, `:132-135` and `ErgoBoxCandidate.scala:194`). The assignment is unconditional, so a nested tree (a Box constant's own tree) overwrites its parent's limit while it parses, as the JVM's does.
2. **Header and size, outside the `try`** (`:145-146`, `deserializeHeaderAndSize` `:217-238`). The header byte, then rule-1012 `CheckHeaderSizeBit` (`'header-version-requires-size'`), then, for a size-flagged header, the declared size, read with `readVlqU32 | 0` (the JVM's `getUInt().toInt`, `:221`): above 2^32−1 it rejects with `ReaderError('vlq-overflow')`; otherwise it wraps to an Int and is never checked. Errors here skip the `finally`, so the limit is not restored, and they reach an enclosing tree's `catch` unchanged.
3. **Constants, then the body, on the same reader** (`:152-186`). For a segregated header the constants count is read with `readVlqU32 | 0`, and constants are read only when it is `> 0` (`deserializeConstants`, `:245-266`): a count that wraps negative gives no constants, and a positive count above 100000 throws `'too-many-constants'` before any constant is read (the JVM's `safeNewArray` bound, `core/.../sigma/util/package.scala:7-18`). The body is one value read (`parseExpr`), every value in the JVM's order (see "Value read order"). With `opts.checkType`, rule 1001 then checks the root's type (see "Rule 1001 on the box paths"). On success the tree is `Parsed` and the cursor stays at the parse end: the declared size plays no part, as in the JVM, whose `propositionBytes` are re-read as `[startPos, r.position)` (`:179-181`).
4. **The degrade** (`:196-209`). A failure in the degrade set (see "ErgoTree union + the soft-fork degrade set" below), the JVM's `ValidationException`, is caught. A size-flagged tree degrades: `numBytes = (bodyPos − start + declared) | 0` (Int arithmetic, `:200`), and the span `[start, start + numBytes)` is checked before it is read. A negative `numBytes`, or one that runs past the end of the input from `start`, throws `ErgoTreeParseError('body-size-overflow')` with the caught error as `cause` (the JVM's `getBytes` fails there, `:202`: a hard reject); in a nested tree, a span past the end throws `'nested-tree-truncated'` instead, with the same `cause`, since the bytes after the enclosing tree in its box may have held it (still a hard reject). Otherwise the cursor, moved back to `start` (scorex's position setter; the JVM's `r.position = startPos`, `:201`), reads the `UnparsedErgoTree`'s bytes with `readBytes(numBytes)`, a detached copy. That re-read begins at `start`, inside the window, so it never trips the window however far it runs (`getBytes` checks once, on entry). In a tree without the size flag the failure is wrapped as `ErgoTreeParseError('soft-fork-without-size-bit')` with the original error as `cause` (the JVM's `SerializerException`, `:204-207`); the wrapper is not in the degrade set, so no enclosing tree degrades on it. Any other failure propagates unchanged, except that a `ReaderError('truncated')` raised in a nested tree's constants or body (inside its `try`; a run-out in its header or size read reaches the enclosing tree unchanged, step 2) is re-thrown by that nested tree as `ErgoTreeParseError('nested-tree-truncated')` with the `ReaderError` as `cause`: still a hard reject, marked, like the nested degrade span above, so that `boxTreeOf`'s miss rule can tell a nested tree's run-out from the tree's own.
5. **`finally`** (`:210-212`) restores the saved position limit, on success and after a degrade, and nothing else.

`parseTree(bytes, opts?)` wraps it with the envelope checks (empty input, the 1 MiB `'oversized'` cap, trailing bytes beyond a sized tree's declared span). The `SBox` value arm and `@ergots/transaction`'s candidate codec reach it through `parseErgoTreeBytes`, which passes `checkType: true`. `forkSubReader` and the old level carry-back are gone from this path (see "Reader depth after a degrade"). A v0 `hasSize=false` tree is the ~99% mainnet-box case (empirically confirmed against the bootstrap-data snapshot at heights 1, 1000, 3849). The mainnet "burn" box at h=545,684 (tx 1, output 0) is `cd 07 02 1a 8e 6f 59 fd 4a`: header `0xcd` (version 5, the size flag, bits 6–7 set), declared size 7, and a body that is a Byte constant `02 1a` followed by five trailing bytes. The lenient parse gives a `Parsed` Byte-constant root with the cursor at byte 4. On the box path rule 1001 fails, the tree degrades, `numBytes = 2 + 7 = 9`, and the box continues at byte 9, as in the JVM (whose tree-version check, enforced only from activated version 2, did not apply at that height; residual 2). Exported within the package for cross-module use by `parse-svalue.ts`.

**ErgoTree union + the soft-fork degrade set (2026-06-17; widened 2026-09-28).** `parseTree` / `parseTreeFromReader` return `ErgoTree = ParsedErgoTree | UnparsedErgoTree` (narrow with `isUnparsedTree`, both exported from the package). A size-flagged tree whose constants, body or root check fails with a JVM-`ValidationException`-equivalent **soft-forkable** error degrades to `UnparsedErgoTree`: its declared span, verbatim, plus the captured error. `serializeTree` re-emits those bytes byte-identically, and `evaluate` / `evaluateWith` reject it with `EvalError('unparsed-ergotree')` (a permanently-unevaluable "burn" script — `@ergots/transaction`'s `validateStateful` thus rejects the spend, as the JVM's interpreter rejects an `UnparsedErgoTree` whose error is not a voted soft fork, `interpreter/.../Interpreter.scala:131-141`). The JVM's fallback (`ErgoTreeSerializer.scala:196-209`) catches `ValidationException` and lets a `SerializerException` escape. `isSoftForkableParseError` covers every error ergots raises for a JVM `ValidationException`, except those of residual 3 (B-full):
- `ExprParseError` / `SValueParseError` `'opcode-reserved'` and `'unknown-opcode'` (`CheckValidOpCode`, rule 1002) and `'soption-tree-version-too-low'` (`CheckSerializableTypeCode`, rule 1009, the Option-typeCode special case at `ValidationRules.scala:135`);
- `SValueParseError` `'register-v6-type'` (rule 1019 `CheckV6Type`), raised by a nested Box's registers once each register's value is read (see `parseAdditionalRegisters`);
- `ErgoTreeParseError` `'root-not-sigma-prop'` (rule 1001) and `'header-version-requires-size'` (rule 1012). Only a nested tree can raise the latter inside a `try`, since a tree reads its own header outside it;
- scorex `ReaderError` `'position-limit-exceeded'` (rule 1014 `CheckPositionLimit`, `core/.../sigma/validation/ValidationRules.scala:169-192`): a checked read that begins past the tree's 4096-byte window, or past a nested Box constant's candidate window (a value's first-byte peek is unchecked; see "Value read order"). The JVM's reader throws the `ValidationException` itself (`CoreByteReader.scala:25-27`), so the inner catch's `ReaderPositionLimitExceeded` arm (`:189-190`) changes nothing.

Everything else rejects: a malformed-data failure (truncation / `vlq-overflow` / `value-out-of-range`), a count above its JVM bound (see "Count bounds inside a tree"), a depth overrun, an **SHeader-DATA constant** (typeCode 104 → a DIRECT `SerializerException` at `CoreDataSerializer.scala:146`, NOT rule-1009-degradable → `'sheader-tree-version-too-low'` REJECTS), and the two wrappers `'soft-fork-without-size-bit'` and `'nested-tree-truncated'`. So an unsized tree failing soft-forkably, nested in a sized tree, rejects the sized tree too, as in the JVM. The broader `ValidationException` class — unknown type codes and method gates, and rule 1009 for SFunc data — degrades in the JVM and rejects in ergots (residual 3; `docs/specs/2026-06-17-ergotree-unparsed-soft-fork-preservation.md` §"B-full residual"). sigma-rust honours the declared size and degrades an empty or short sized body (e.g. `[08 00]`); ergots, like the JVM, reads such a body on from whatever bytes follow. Conformance: SANTA `ErgoTree.unparsed_soft_fork_roundtrip` (`0b01fd` / `0b03fd0102`) and `Box.softfork_header_constant_reject` (both `jvm:sigma-state-6.0.3`); `Box.sized_tree_declared_size` (santa `2b1acee`), `Box.tree_read_window` and `Box.tree_root_type_check` (santa `9421c11`), all `jvm:sigma-state-6.0.6`. Specs: `docs/specs/2026-06-17-ergotree-deserialize-unification.md`, `docs/specs/2026-09-28-sized-tree-declared-size-design.md`.

**Reader depth after a degrade (the JVM's level leak, 2026-09-27; native since 2026-09-28).** Every JVM deserialize frame (`ValueSerializer.deserialize`, `CoreDataSerializer.deserialize`, `DataSerializer`'s Box and Header arms, `SigmaBoolean.serializer.parse`) raises `r.level` on entry and lowers it with `r.level = r.level - 1` only when it returns normally; there is no `finally` (sigma-state v6.0.6 `ValueSerializer.scala:396-411`). When `deserializeErgoTree` catches the soft-fork `ValidationException` and degrades the tree, its `finally` restores only the position limit (`ErgoTreeSerializer.scala:196-212`). So the levels of every frame that was active when the failing node threw stay on the reader, through the enclosing frames' normal exits, for the rest of that reader's parse: later registers, outputs and extension values of the same transaction have that many fewer levels left. ergots does the same, natively: its frames (each value read by `parseExpr`, each data value by `parseSValue`, each register value and register Tuple item, each SigmaBoolean node by `parseSigmaBoolean`, and `@ergots/transaction`'s context-extension value) lower the level only on a normal return, and `parseTreeFromReader` parses on the one reader the enclosing parse uses. A leaked level is therefore already where the JVM has it, whether the tree degrades or parses around a degrade nested in its body (a Box constant's own sized tree); nothing carries it across a reader boundary, because there is none. In ergots a degrade is the only point where parsing continues after a caught throw. Residual: ergots degrades on six opcodes the JVM parses (the `'opcode-reserved'` entry in the error taxonomy below), so for those it leaks levels the JVM does not. Conformance: SANTA `Transaction.degraded_tree_depth_leak` (`jvm:sigma-state-6.0.6`): a tree degrading at depth 10 leaves 10 levels, so a later register `Coll^99[Byte]` parses (10 + 1 + 99 = 110) and `Coll^100[Byte]` rejects. SANTA `Transaction.nested_degrade_depth_leak` (santa@fb35b8d, same blesser) pins the nested case: the same tree as a Box constant inside a size-flagged tree that parses leaves the same 10 levels, with the same two verdicts.

**Rule 1001 on the box paths (2026-09-28).** Rule 1001 `CheckDeserializedScriptIsSigmaProp` (`org/ergoplatform/validation/ValidationRules.scala:39-52`) requires a tree's root to type as SigmaProp. The JVM runs it when `checkType` is set (`ErgoTreeSerializer.scala:173-175`), and every main-code caller sets it: the box parser (`ErgoBoxCandidate.scala:194`), `ErgoTree.fromBytes` (`sigma/ast/ErgoTree.scala:413-415`) and address decoding (`ErgoAddress.scala:322`). Only the `private[sigma]` 3-argument `deserializeErgoTree` can pass `false`; SANTA's blesser uses it for the ErgoTree wire kind (`LenientErgoTree.scala:22`). ergots runs rule 1001 on:
- box ingest: `parseErgoTreeBytes`, so the `SBox` value arm and `@ergots/transaction`'s candidate codec;
- the spend: `@ergots/transaction` evaluates `boxTreeOf(selfBox.ergoTreeBytes)`, the ingest parse, as the JVM evaluates `box.ergoTree` (ergo-core `ErgoTransaction.scala:138`); `boxTreeOf`'s miss parse applies it too;
- P2S address decoding (`ergoTreeFromAddress`).

`parseTree` is lenient by default and takes `{ checkType: true }` to opt in.

The root's type is `exprTpe(root)`, the node's own type as the JVM computes it: `If` takes its true branch's (`sigma/ast/trees.scala:1351`), and `Apply` takes the function's range for an `SFunc`, the element type for a collection, and `NoType` otherwise (`sigma/ast/values.scala:1247-1251`). `exprTpe`'s `Apply` arm matches that: an `SFunc` function gives its range; an `SColl` function gives its element type; a function typed as the JVM's `SAny` or `NoType` gives the JVM's `NoType`, `NOTYPE_JVM` (2026-09-29; it gave the function's `SAny` before), and ergots' own `SAny` stays itself (see below); any other function type throws `ExprTpeError('apply-func-no-type')`, the JVM's `NoType` (an `STuple` extends the JVM's `SCollection` trait but is not an `SCollectionType`, `core/.../sigma/ast/SType.scala:766,838`, so it is `NoType` too). `ByIndex` takes its input's element type (`ByIndex.tpe = input.tpe.elemType`, `sigma/ast/transformers.scala:254`), and a tuple's element type is the JVM's `SAny` (`STuple` extends `SCollection[SAny]` with `elemType = SAny`, `SType.scala:838-841`): `exprTpe` gives `ByIndex` over a tuple `SANY_JVM` (2026-09-29; it threw `'by-index-input-not-scoll'` before, which the rule rejected hard where the JVM degrades a sized tree). The rule then reads:
- `SSigmaProp` passes;
- ergots' own `SAny` passes (residual 1): the fresh object its method typing returns where it has no result type to give (a method its catalog lacks, or a type variable left unbound), and the element type `unifyTypes` gives a tuple matched against a collection (the JVM makes that one `SAny` too, `core/.../sigma/ast/package.scala:46-47`, and fails such a root);
- any other type, the JVM's `SAny` (`SANY_JVM`) and `NoType` (`NOTYPE_JVM`) included, as in the JVM, or `'apply-func-no-type'`, throws `ErgoTreeParseError('root-not-sigma-prop')`. That code is in the degrade set: a sized tree degrades to its declared span, and a tree without the size flag rejects as `'soft-fork-without-size-bit'`;
- any other `ExprTpeError` propagates as a hard reject: each is a shape the JVM throws for while it builds or types the node, a `ClassCastException`, an `IllegalArgumentException` from a `require`, or an index error (`ByIndex` over a type that is no collection, `OptionGet` or `OptionGetOrElse` over one that is no option, `SelectField` over one that is no tuple or past its arity, `Map` with a mapper that is no function; `sigma/ast/transformers.scala:38, 254, 294, 601, 626`; and, since 2026-09-29, the JVM's `SAny` or `NoType` through an arm that casts or requires its input's type, below). None is a `ValidationException`, so none degrades. A shape the JVM types, `exprTpe` must type too, or the rule over-rejects: `ByIndex` over a tuple was one, until 2026-09-29. `ExprTpeError` is root-exported so callers can classify it.

**The JVM's `SAny` versus ergots' own (2026-09-28; a tuple's element type, 2026-09-29).** The JVM fails a root whose type is `SAny`: rule 1001 requires `root.tpe.isSigmaProp`, an `isInstanceOf[SSigmaProp.type]` (`core/.../sigma/ast/package.scala:121`). Type code 97 parses as `SAny` (`TypeSerializer.scala:196`), `GetVar` and `DeserializeContext` are built with no type check (`SigmaBuilder.scala:479-480, 607-608`), and `OptionGet.tpe = input.tpe.elemType` (`sigma/ast/transformers.scala:601`), so `00 e4 e3 01 61` (`OptionGet(GetVar(1, SAny))`) and `00 d4 61 01` (`DeserializeContext(SAny, 1)`) root as `SAny` and fail it; an `Apply` of such a function is `NoType` and fails it too. A tuple's element type is the same `SAny` (`STuple` extends `SCollection[SAny]`, `SType.scala:838-841`), so `ByIndex` over a tuple roots as `SAny` too (`ByIndex.tpe = input.tpe.elemType`, `sigma/ast/transformers.scala:254`): `08 0a b2 86 02 04 00 04 00 04 00 00` degrades in the JVM, and a ValDef bound to it types as `SAny` (`ValDef.tpe = rhs.tpe`), so `08 10 d8 01 d6 01 b2 86 02 04 00 04 00 04 00 00 08 d3` parses. ergots' method typing also makes `SAny`s of its own, which pass the rule (residual 1). The two are told apart by identity. `SANY_JVM` (`mir/types.ts`) is one frozen object: `parseSType` returns it for type code 97, nested or not, and `exprTpe` returns it for `ByIndex` over a tuple; every node stores the type it parsed as received (no clone between `parseSType` and `exprTpe`); and wherever `exprTpe` passes an `SAny` through, it returns its input's object rather than a fresh one, as a `ValUse` returns the type its `ValDef` stored (where the JVM casts or requires the input's type instead, `exprTpe` throws for the JVM's `SAny`; see the next paragraph). ergots' own `SAny` is always a fresh object: an unregistered method's return, `resolveReturnTpe`'s fallback for a type variable that cannot bind, and `unifyTypes`' element type for a tuple unified as a collection (which the JVM computes as its `SAny`, residual 1). Structurally both are `{ tag: 'SAny' }`, so equality checks and `serializeSType` treat them alike. So the JVM's `SAny` fails the rule when it reaches the root through `exprTpe`'s own arms; where the method typing replaces it with one of ergots' own, it passes (residual 1: `00 db 24 03 e3 01 61`, `SOption.get` on `GetVar(1, SAny)`, whose `(typeId, methodId)` the catalog lacks, parses under `checkType`). Telling the two apart cannot itself reject an honest tree, since ergots' own `SAny` keeps passing; the rule can over-reject only where `exprTpe` throws for a shape the JVM types, as it did for `ByIndex` over a tuple until 2026-09-29 (see the rule's reading above).

**The JVM's `SAny` through an arm that casts or requires its input's type (2026-09-29, final fix round 2).** `exprTpe` mirrors the JVM node's `tpe`, including where that `tpe` throws. The JVM casts an input's type to the class it needs:
- while it builds the node, in `ByIndex` (`val tpe = input.tpe.elemType`, `sigma/ast/transformers.scala:254`), `SelectField` (`val tpe = input.tpe.items(fieldIndex - 1)`, `:294`), `Map` (`val tpe = SCollection(mapper.tpe.tRange)`, `:38`), `Slice` and `Append` (`val tpe = input.tpe`, `:89`, `:62`), and `OptionGet` and `OptionGetOrElse` (`def tpe = input.tpe.elemType`, read by the `val opType`, `:600-601`, `:625-626`);
- wherever the node's type is read, in `Filter` (`def tpe: SCollection[IV] = input.tpe`, `:121`).

A cast of the JVM's `SAny` or `NoType` throws a `ClassCastException`, so the tree rejects hard, sized or not. `exprTpe` throws the arm's `'<arm>-input-class-cast'` code (`'map-mapper-class-cast'` for `Map`) for an input typed `SANY_JVM` or `NOTYPE_JVM`. The JVM also requires a numeric type or `NoType` (`isNumTypeOrNoType`, `core/.../sigma/ast/package.scala:139`) while it builds `Negation` (`sigma/ast/trees.scala:882`), `BitInversion` (`:900`) and `BitOp` (`:913`, the left operand's type and then the right's). Its `SAny` fails the require, an `IllegalArgumentException` that the tree parse rethrows as a `SerializerException` (`ErgoTreeSerializer.scala:190-193`), hard; `NoType` passes it. `exprTpe` throws `'negation-input-jvm-sany'`, `'bit-inversion-input-jvm-sany'` or `'bit-op-operand-jvm-sany'` for an input typed `SANY_JVM`, and passes `NoType` through, `NOTYPE_JVM` and the `'apply-func-no-type'` throw alike. ergots' own `SAny` passes every arm.

`NOTYPE_JVM` (`mir/types.ts`) is the JVM's `NoType` from its `SAny`: an `Apply` whose function types as `SANY_JVM` or `NOTYPE_JVM` (`sigma/ast/values.scala:1247-1251`). It fails the casts and rule 1001, and passes the numeric requires, which is why it is not `SANY_JVM`. An `Apply` of a function whose type is concrete, and neither a function nor a collection, still throws `'apply-func-no-type'` (residual 8).

The arms the JVM types keep typing both: `If` (its true branch, `trees.scala:1351`), `BlockValue` and `ValDef` (`values.scala:1015, 953`), `Fold` (its zero, `transformers.scala:222`), arithmetic (its left operand, with no cast, `trees.scala:707-708`; the pre-v3 builder upcasts only numeric pairs), `Tuple` and `FuncValue` (wrapped, `values.scala:812, 1057-1064`), and `SizeOf`, `Exists`, `ForAll`, `OptionIsDefined`, the relations and the logical operators, whose types are fixed. A live sigma-state 6.0.6 probe fixed every verdict: 21 arms, each over `ByIndex` over a tuple, `GetVar` and `DeserializeContext` of type code 97, and an `Apply` of either, at a sized root, an unsized root, a root parsed without `checkType`, and a ValDef's right-hand side (`test/wire/rule-1001-jvm-sany-arms.test.ts`).

`exprTpe` reads a child's type only where the JVM does. A `PropertyCall` with explicit type arguments (`Global.none[T]`, 106:10) is typed from those alone, as the JVM never reads its object's type (`PropertyCallSerializer.scala:36-50`): `0b 16 e4 db 6a 0a b5 b2 86 02 04 00 04 00 04 00 00 d9 01 01 04 01 01 08` (`OptionGet(Global.none[SigmaProp])` on a `Filter` over `ByIndex(tuple)`) parses in both.

The JVM makes these checks wherever the node sits (for `Filter`, wherever its type is read). ergots makes them only where it types a node: the root under `checkType`, a ValDef's right-hand side, and the arms `exprTpe` descends from there. So ergots parses, where the JVM rejects, such a node at a root parsed without `checkType` (`00 b4 b2 86 02 04 00 04 00 04 00 00 04 00 04 02`, `Slice` over `ByIndex(tuple)`) and such a node whose type no enclosing node reads (`08 10 b1 b4 b2 86 02 04 00 04 00 04 00 00 04 00 04 02`, `SizeOf` of that `Slice`, which degrades in ergots): the spec's node-construction follow-up. `Upcast` and `Downcast` are not checked even where ergots types a node. The JVM requires a numeric input while it builds them (`sigma/ast/trees.scala:398, 431`), which its `SAny`, its `NoType` and any other non-numeric type fail, where `exprTpe` types them from their target without reading the input. The JVM also reads more types while it builds some nodes than `exprTpe` reads to type them: all three children of an `If` (`Quadruple.opType`, `sigma/ast/trees.scala:1313`), both operands of arithmetic, and the input of `OptionIsDefined` (`transformers.scala:656`) and `SigmaPropBytes` (`:336`). So a `Filter` over the JVM's `SAny` in those places rejects in the JVM and parses in ergots, for example in an `If`'s false branch at the root. Both belong to the same follow-up, the next spec.

A spend of a box whose tree rule 1001 degraded therefore rejects (`EvalError('unparsed-ergotree')`), as the JVM's interpreter rejects an `UnparsedErgoTree` whose error is not a voted soft fork (`Interpreter.scala:131-141`). The root `Apply` of a `Coll[SigmaProp]` (`00 da 14 01 d3 01 04 00`) types as SigmaProp and passes; the root `Apply` of an Int (`08 06 da 04 00 01 04 00`) is `NoType` and degrades. The evaluator's own `exprTpe` callers see the same `Apply` typing: for them too the collection case is the JVM's type, and a non-function still throws. Conformance: SANTA `Box.tree_root_type_check` / `Transaction.tree_root_type_check` (santa `9421c11`, `jvm:sigma-state-6.0.6`): an unsized SigmaProp root is accepted, an unsized Int root rejected, a sized Int root degraded and accepted.

**Value read order (2026-09-28).** The JVM reads every value in three steps (`ValueSerializer.deserialize`, `ValueSerializer.scala:396-411`):
1. It raises the reader level. The setter throws `DeserializeCallDepthExceeded` above the cap (`CoreByteReader.scala:127-131`).
2. It **peeks** the first byte with `peekByte`, which has no window check (`CoreByteReader.scala:41`). At the end of the input the peek throws a raw index exception, a hard reject.
3. It does the window-checked read of that byte (a constant's type code, or an opcode).

ergots does the same wherever the JVM runs `ValueSerializer.deserialize`: `enterDepth()`, then scorex's `peekU8()` (at the end of the input a hard `ReaderError('truncated')`), then the checked read. That covers `parseExpr` (every Expr, including a tree's body), each register value and each register Tuple item, and `@ergots/transaction`'s context-extension value. Relation2 (`trees/Relation2Serializer.scala:40-52`) peeks the same way for the packed Boolean pair `0x85` and consumes it only on that path; otherwise the left operand is read as a full value. Searching sigma-state's main code for `peekByte()` finds only these two peek sites. So a value read that starts past the window at the end of the input is a hard reject, not a rule-1014 degrade, and a depth error beats a window error when both apply. Only value reads peek: a data read at the end of the input meets the window check first and degrades a sized tree — for example the `Int` inside a `(Coll[Byte], Int)` constant, read with `getInt`, which checks the window before it reads (`CoreByteReader.scala:63-66`); ergots' data reads likewise check the window before the end of input. SANTA pins the peek with `Transaction.tree_read_window` #0 and #1 (santa `9421c11`), which differ only in whether another output follows the tree: with one, the read past the window degrades the sized tree; without one, the peek fails and the transaction rejects. For a tree whose next value read begins past its window at the very end of its transaction, the JVM's verdict thus depends on what follows it in the block (residual 7).

**Count bounds inside a tree (2026-09-28).** Every count the parser reads inside a tree has its JVM reader and bound, and above the bound the parse rejects: hard, not in the degrade set, as the JVM's `safeNewArray` `RuntimeException` and the `SerializerException` that the inner catch makes of `getUShort`'s `IllegalArgumentException` (`ErgoTreeSerializer.scala:188-194`) escape its degrade. Below the bound the window decides. That matters since the window degrades a sized tree: a count read with no bound, or with a laxer one, would let the window turn a JVM reject into an ergots accept.
- **Apply and MethodCall arguments** (`SigmaByteReader.getValues`, `SigmaByteReader.scala:53-61`, called from `ApplySerializer.scala:24` and `MethodCallSerializer.scala:51`), **BlockValue items** (`BlockValueSerializer.scala:28-37`), **FuncValue arguments** (`FuncValueSerializer.scala:30-34`) and **SigmaAnd and SigmaOr items** (`transformers/SigmaTransformerSerializer.scala:20-29`): a u32 that must fit an Int (`getUIntExact`), at most 100000 (`safeNewArray`, `core/.../sigma/util/package.scala:7-18`). The four existing caps (`'apply-too-many-args'`, `'method-call-too-many-args'`, `'block-too-many-items'`, `'func-value-too-many-args'`) move from 65536 to 100000; SigmaAnd and SigmaOr items, which had no bound, get the same one (`'sigma-and-too-many-items'`, `'sigma-or-too-many-items'`).
- **ConcreteCollection and Boolean-constant collection items** (`ConcreteCollectionSerializer.scala:27-41`, `ConcreteCollectionBooleanConstantSerializer.scala:33-47`): at most 0xFFFF (`getUShort`), checked while parsing, right after the count and before the element type is read, as the JVM's `getUShort` throws before `getType` (`ConcreteCollectionSerializer.scala:28-29`). The code is `'collection-size-out-of-range'`, which until now only the serializer raised.
- **The segregated constants count**: `readVlqU32 | 0`, read only when `> 0`, above 100000 `'too-many-constants'` (step 3 of `parseTreeFromReader`).

The error codes keep their names and now mean "above the JVM's bound". The same rule, the JVM's reader and the JVM's order, also reaches these reads:
- **CTHRESHOLD** (`core/.../sigma/data/SigmaBoolean.scala:94-101`): `k`, then `n`, each a `getUShort`, so `k` above 0xFFFF rejects as it is read, before `n` is read (`'cthreshold-k-out-of-range'`), and `n` above 0xFFFF likewise (`'arity-out-of-range'`); then the `n` children; only then the JVM's `CTHRESHOLD` `require` (`:223`): `k > n` (`'cthreshold-k-out-of-range'`) and `n > 255` (`'arity-out-of-range'`). ergots' own stricter checks sit where they cannot pre-empt a child's window error: `n < 1` (`'sigma-conjecture-empty-items'`) before the children, where it reads nothing either way, and `k < 1` (`'cthreshold-k-out-of-range'`) with the `require`, after them. So a child that trips the window degrades a sized tree whatever `k` and `n` say, as in the JVM.
- **A register Tuple's arity** (a nested Box's registers are read inside its tree): a signed `getByte`, then `safeNewArray` (`TupleSerializer.scala:28-31`), so an arity of 128 or more rejects before any item is read (`'sbox-register-tuple-arity'`). ergots also rejects an arity below 2, which the JVM parses (residual 4).
- **Data lengths.** An SString length is a `getUIntExact` (`CoreDataSerializer.scala:104-110`), so above `Int.MaxValue` it rejects (`'string-too-long'`) before the window check of its bytes. SBigInt and UnsignedBigInt lengths are `getUShort().toShort` (`:111-117`, `:118-124`): above 0xFFFF a hard reject; then the low 16 bits as a signed Short, above 32 rejected at once (`'bigint-too-large'`, `'unsigned-bigint-too-large'`); a size of 0 or a negative Short goes to `getBytes`, whose window check comes first, then the reject (`'bigint-empty'` for an SBigInt of size 0, else too-large). An UnsignedBigInt of size 0 is `0`.
- **Type code 0** (`TypeSerializer.scala:133-135`): the JVM's `InvalidTypePrefix` message evaluates `r.getBytes(r.remaining)`, a window-checked read, so past the window the window error (rule 1014, a degrade) comes before `'invalid-type-code'`.
- **Header points** (`ErgoHeader.scala:73-74, 90`): an SHeader value's `minerPk`, and a v1 header's `powOnetimePk`, are validated as each is read, through `parseHeader`'s `validatePoint` option ([`facts/scorex.md`](./scorex.md)), so an invalid point rejects (`'group-element-invalid-point'`) before a later read can trip the window. A v1 solution's `d` is read even when its length byte is 0 (`:76-77`), so that read's window check is made.
- **Ids.** FuncValue argument ids and ValUse ids are `getUInt().toInt` (`FuncValueSerializer.scala:36`, `ValUseSerializer.scala:13`): a u32, above which the read rejects (`ReaderError('vlq-overflow')`), wrapped to an Int (Round-trip Carve-out 5). A ValDef id is `getUIntExact` (`ValDefSerializer.scala:31`): a u32 at most `Int.MaxValue` (`'val-def-id-out-of-range'`).
- **The `0x85` lookahead** belongs to Relation2's nine opcodes only (GT, GE, LT, LE, EQ, NEQ, BinOr, BinAnd, BinXor; `ValueSerializer.scala:48-58`); the arithmetic and bit operators read two full values (see "Value read order").

The `getUShort` over-long-VLQ quirk is a follow-up: the JVM reads `getULong().toInt` before its range check, so it accepts an over-long VLQ whose low 32 bits are in range, which ergots rejects. It applies at every `getUShort` read: the collection counts, the SigmaBoolean counts and `k`, the BigInt and UnsignedBigInt lengths, the SBox index, and `@ergots/transaction`'s io counts and proof length.

**`substituteConstantsBytes(...)`** is the byte-surgery behind the `SubstConstants` eval arm. It mirrors JVM `ErgoTreeSerializer.substituteConstants` (`ErgoTreeSerializer.scala:320-411`): the header + constants segment are re-parsed and re-serialized, but the tree BODY is copied **verbatim** — never parsed as an `Expr`. This is the consensus-faithful behavior: a crafted template whose body is not valid Expr bytes is returned unchanged (0 constants ⇒ no substitution) where a full `parseTree` throws. ergots **leads** this fix — sigma-rust still uses the parse-based `with_constant` and shares the divergence (routed to sigma-rust); JVM is canonical. JVM-parity details encoded in the fn (`ErgoTreeSerializer.scala:286-411`):

- Out-of-range positions (negative or `>= numConstants`) are a silent no-op; duplicate positions are FIRST-wins (`getPositionsBackref:286-299`).
- Every constant (substituted or not) is re-serialized via `serializeSType`/`serializeSValue` (matching JVM's `constantSerializer`), so the constants segment is NOT a verbatim copy — only the body is.
- The size prefix is re-emitted only when `treeVersion >= 3` (`isV3OrLaterErgoTreeVersion`, the V6 soft-fork; `:369-375`); for the v≤2 range ergots evaluates it is dropped, so a `hasSize` template's output omits the size slot — exactly as JVM does. `treeVersion` is the evaluation's ErgoTree version, NOT the template header's.
- The template's header and size are read as `deserializeHeaderWithTreeBytes` reads them (`:269-274`, through `deserializeHeaderAndSize`): rule 1012, then, for a size-flagged header, the declared size with `readVlqU32` (above 2^32−1 `ReaderError('vlq-overflow')`), otherwise unused. The constants count follows `deserializeConstants` (`:245-266`), as in the tree parse: `readVlqU32 | 0`, constants read only when it is `> 0` (a count that wraps negative gives none), above 100000 `'too-many-constants'`.
- The size field does NOT bound the body read (`treeBytes = r.getBytes(r.remaining)`); the body is all remaining bytes.

New `ErgoTreeParseError` codes from this fn: `'subst-length-mismatch'`, `'subst-type-mismatch'` (the eval arm re-wraps them as `EvalError('subst-constants-error')`).

## Round-trip invariant

For any byte sequence `b` accepted by `parseTree`:

```
serializeTree(parseTree(b)) === b   (byte-equal)
```

This holds for every ErgoTree variant we ship. The corpus test asserts this on 255 passing fixtures plus 1 mainnet-fixture stub plus 6 upstream-buggy fixtures (the 6 are excluded from byte-equality; sigma-rust itself does not round-trip them — see `fixture-gen/known_unstable.json`).

**Carve-out 1 — arity-0/1 generic-tuple TYPE:** trees whose serialized types include an arity-0/1 generic-tuple TYPE (`0x60` + len 0/1) PARSE but cannot re-serialize — `serializeSTuple` throws `'tuple-too-short'`, mirroring the JVM's own asymmetry (`TypeSerializer.scala:188-194` parse has no arity require; `:93-94` serialize `sys.error`s < 2). The reverse-direction precedent is the AvlTree any-length-digest note.

**Carve-out 2 — noncanonical Option tags:** any wire Option tag byte > 0x01 parses as Some (JVM scorex-util `getOption`: ANY nonzero = Some) but re-serializes to the canonical `0x01` — so `serializeTree(parseTree(b)) ≠ b` for trees carrying noncanonical tags (SOption DATA constants, `DeserializeRegister.default`, `ByIndex.default`, SAvlTree `valueLengthOpt`). The JVM has the identical asymmetry (`putOption` emits 1/0); it round-trips such trees only because `ErgoTree` RETAINS original bytes rather than re-serializing (`ErgoTree.scala:65-67,123-131`) — ergots likewise retains verbatim slices where consensus reads the bytes as received (SBox `ergoTreeBytes` for R1 and `propositionBytes`; a parsed box's retained slice for its `bytes` and id). Where the JVM re-serializes a box it normalizes these tags, and so does ergots: tx ids and the signing message, constructed boxes' `bytes` and ids, the box-size and dust checks, and `bytesWithoutRef` write the tree through `reencodeTreeBytes` (see "Box trees"). Tooling note: `addressFromErgoTree` re-serializes, so a noncanonical on-chain tree yields a different P2S address than a JVM node derives from retained bytes — tooling-level, not consensus.

**Carve-out 3 — noncanonical identity GroupElements:** a GE payload with lead byte 0x00 and ANY bytes 1..32 (SValue GE data, ProveDlog/ProveDHTuple leaf points) parses as the identity and re-serializes CANONICAL (33 zeros) — so `serializeTree(parseTree(b)) ≠ b` for trees carrying garbage-tail identity encodings. The JVM behaves identically at the value layer (`GroupElementSerializer.parse` reads ANY 0x00-lead into the identity point object; serialize emits 33 zeros, :20-42) and round-trips such trees only via retained original bytes (the same mechanism as Carve-out 2). Box re-serializations normalize these encodings, as the JVM's do: tx ids, constructed boxes' `bytes` and ids, the box-size check and `bytesWithoutRef` write the tree through `reencodeTreeBytes` (see "Box trees"). Invalid non-0x00-lead payloads now REJECT at parse (`'group-element-invalid-point'` / `'ec-point-invalid'`) instead of round-tripping raw — the old byte-faithful raw retention matched NEITHER reference's value semantics. See `GroupElement canonical parse` below.

**Carve-out 4 — a declared size that differs from the body (2026-09-28; supersedes the 2026-06-17 carve-out and its boundary residual).** The declared size no longer bounds the parse: a size-flagged tree is parsed on the arriving reader, its declared size is used only if it degrades, and `serializeTree` writes a parsed tree's true size. So a tree whose declared size is larger ("over") or smaller ("under") than its body parses the whole body, the cursor stops at the parse end, and the tree does not round-trip: `09 03 08 d3` and `09 01 08 d3` both re-serialize to `09 02 08 d3`, as in the JVM (SANTA `Box.sized_tree_declared_size` / `Transaction.sized_tree_declared_size`, santa `2b1acee`, `jvm:sigma-state-6.0.6`: the JVM accepts all six entries and re-serializes both mismatches to the control's bytes). `parseTree` tolerates bytes after the parse end that lie within a size-flagged tree's declared span (`bodyPos + declared`, where the retired bounded sub-reader ended), so `09 03 08 d3 00` parses; a byte beyond that span throws `'trailing-bytes'` (ERG-02; residual 6). On the box path the span as received is kept on `ergoTreeBytes` (R1, `propositionBytes`), and every box re-serialization writes the re-encoded tree (`reencodeTreeBytes`, see "Box trees"), as the JVM's candidate serializer does, so ids and re-serialized boxes carry the true size. Adversarial-only: an honest tree's declared size equals its body. The mainnet burn box h=545,684 (`cd 07 02 1a 8e 6f 59 fd 4a`) parses leniently to a `Parsed` Byte-constant root that re-serializes as `cd 02 02 1a`; on the box path rule 1001 degrades it to its declared span, which re-encodes to its raw bytes, and the box continues at byte 9, as in the JVM.

**Carve-out 5 — FuncValue argument ids and ValUse ids outside [0, 2^31) (2026-09-28).** The JVM reads both ids with `getUInt().toInt` (`FuncValueSerializer.scala:36`, `ValUseSerializer.scala:13`): a u32, above which the read rejects (`ReaderError('vlq-overflow')` here), wrapped to an Int, so an id from 2^31 up parses as a negative Int, `0xFFFFFFFF` as −1 (the table at `DeserializationResilience.scala:366-380`). ergots reads them the same way (`readVlqU32(r, …) | 0`). The wrap is a bijection on [0, 2^32), and an argument id and a ValUse id wrap alike, so each ValUse still resolves to the same argument, and evaluation is unchanged (the evaluator's bindings are a `Map` keyed by the id, `eval/env.ts`). Such a tree parses but cannot be re-encoded. The JVM writes both ids with `putUInt` (`FuncValueSerializer.scala:23`, `ValUseSerializer.scala:9`), which rejects a negative Int (`"-1 is out of unsigned int range"`, scorex-util 0.2.1 `VLQWriter.scala:64-67`, pinned by `DeserializationResilience.scala:386-389`); `serializeFuncValue` and `serializeValUse` reject an id outside [0, 2^31) with `ExprSerializeError('func-value-arg-id-out-of-range')` and `ExprSerializeError('val-use-id-out-of-range')`. The id domain is a JVM Int, of which `putUInt` takes [0, 2^31): a parse yields only Ints, and rejecting there the negative ones mirrors the JVM, while an id at or above 2^31, which would re-parse as a different id, or a non-integer can only come from hand-built MIR (as `serializeValDef` bounds its id at `Int.MaxValue`). So the JVM rejects a transaction whose output tree carries such an id at parse, since ergo-core computes the transaction id eagerly (`ErgoTransaction.scala:68`), re-encoding every output tree; `parseTransaction` rejects it as `TxParseError('output-tree-not-reencodable')` ([`facts/transaction.md`](./transaction.md)). Adversarial-only: honest trees carry small ids (the largest in the committed corpus and mainnet fixtures is 87).

**Carve-out 6 — an SAvlTree constant's `keyLength` or `valueLengthOpt` at or above 2^31 (2026-09-28; the same shape as Carve-out 5, for `AvlTreeData` rather than `FuncValue`/`ValUse`).** The JVM reads both fields with `getUInt().toInt` (`AvlTreeData.scala:84-85`): a u32, above which the read rejects (`ReaderError('vlq-overflow')` here), wrapped to an Int, so a value from 2^31 up parses as a negative Int — the `SAvlTree.keyLength` / `.valueLengthOpt` i32 view (`facts/ergoscript-eval.md`). ergots reads them the same way (`readVlqU32`). Such a tree parses but cannot be re-encoded. The JVM writes both fields with `putUInt` (`AvlTreeData.scala:77-78`), which rejects a negative Int (`"… is out of unsigned int range"`, pinned by `DeserializationResilience.scala:386-395`); `serializeSValue`'s `SAvlTree` arm rejects a `keyLength` or `valueLengthOpt` outside `[0, 2^31 - 1]` with `'savltree-key-length-out-of-range'` / `'savltree-value-length-out-of-range'` (was `[0, 2^32 - 1]`). So the JVM rejects a transaction whose output tree carries such a value at parse, for the same reason as Carve-out 5 — `ergo-core` re-encodes every output tree eagerly to compute the transaction id, so `parseTransaction` rejects it as `TxParseError('output-tree-not-reencodable')` ([`facts/transaction.md`](./transaction.md)). Adversarial-only: honest trees carry small `keyLength`/`valueLengthOpt` values (1, 8, 32 and 64 across the committed corpus).

**Carve-out 7 — an `STypeVar` name whose re-encoding exceeds 255 bytes (2026-09-29; the same shape as Carve-outs 5 and 6).** The JVM reads a name as a `getUByte` length and that many bytes, decoded with `new String(bytes, UTF_8)` (`TypeSerializer.scala:202-205`), which turns each ill-formed unit into one U+FFFD; `STypeVar`'s `require(name.length <= 255)` counts UTF-16 chars (`SType.scala:288`), so a 255-byte name always parses. It writes the name back as `name.getBytes(UTF_8)` with `putUByte(bytes.length)` (`:122-126`), and scorex-util's `putUByte` requires at most 255, where each U+FFFD is 3 bytes: 86 or more `0xff` bytes parse to a name that cannot be written. ergots decodes the same way (`decodeUtf8Lossy`, see `STypeVar` name below) and `serializeSType` rejects the name with `STypeSerializeError('stypevar-name-length')`. One carrier is a `FunDef` type argument. The JVM rejects a transaction whose output tree carries such a name at parse, for the same reason as Carve-out 5, and `parseTransaction` rejects it as `TxParseError('output-tree-not-reencodable')` ([`facts/transaction.md`](./transaction.md)). Adversarial-only: honest tools never emit a malformed type-variable name.

**Carve-out 8 — a node the JVM writes through another serializer than the one it was read with (2026-09-29).** The JVM writes a parsed tree from its structure, each node through the serializer its `companion` picks, whichever opcode the node was read with; ergots' serializers follow it:
- a `ConcreteCollection` whose element type is `SBoolean` and whose items are all constants (`isBooleanConstants`, `sigma/ast/values.scala:871-875`) is written as a Boolean-constant collection, `0x85` with packed bits (`ConcreteCollectionBooleanConstantSerializer.scala:16-30`), empty included: `00 d1 96 83 02 01 01 01 01 00` re-encodes as `00 d1 96 85 02 01`, and `00 d1 96 83 00 01` as `00 d1 96 85 00`. A placeholder is not a constant, so a collection holding one stays `0x83`. A collection of constants one of which is not a Boolean cannot be written (`ExprSerializeError('collection-item-not-boolean-constant')`), as the JVM's serializer fails on it (`:22-27`). The JVM's parse rejects such a tree first, on its item-type assert (`ConcreteCollectionSerializer.scala:38`), which ergots does not make (residual 9), so `parseTransaction` rejects an output carrying one as `'output-tree-not-reencodable'`: the JVM's verdict, at another stage.
- a `MethodCall` without arguments is written as a `PropertyCall` (`companion = if (args.isEmpty) PropertyCall else MethodCall`, `values.scala:1351`; `PropertyCallSerializer.scala:20-28`): `0xdb` and no argument count, so `00 d1 91 dc 63 01 a7 00 05 00` re-encodes as `00 d1 91 db 63 01 a7 05 00`, and a sized tree's size is recomputed. In a v3 or later tree the JVM rejects such a call at parse (`MethodCallSerializer.scala:53-55`), which ergots does only before evaluation (the spec's follow-ups).

Such a tree does not round-trip, and the re-encoding is what the JVM writes for the transaction id, the output ids, `Global.serialize` and the serialize cost (sigma-state 6.0.6 probe, transaction ids included). sigma-rust writes both nodes back as read. A JVM-compiled tree is already in this form, and so is every tree in the chain's served bytes, which are the JVM's re-encoding: none of the 12,885 mainnet trees in the committed fixtures carries either shape.

**Carve-out 9 — a Box constant whose index is 0x8000 or more (2026-09-29; the same shape as Carve-outs 5–7).** The JVM holds a box's index as a Short: it reads `getUShort()` and stores `index.toShort` (`ErgoBox.scala:56, 218, 224`), so 0x8000–0xFFFF parse to a negative Short, and it writes the index back with `putUShort` (`:211`), which rejects a negative value (scorex-util 0.2.1 `VLQWriter.scala:36-39`: "Value -32768 is out of unsigned short range"). Such a box parses, and its `bytes` and id use the bytes as received (`:87-92`; `boxBytesOf`), but it cannot be re-encoded: the SBox write takes [0, 0x7FFF] and rejects any other index with `SValueSerializeError('sbox-index-out-of-range')`, while the parse bound stays 0xFFFF. The JVM rejects a transaction carrying one at parse in every placement, since its eager id writes the whole signing message: a Box constant in an output tree, which `parseTransaction` rejects as `'output-tree-not-reencodable'`, and a Box value in an output register or a context extension, which ergots rejects when it computes the id (residual 4; [`facts/transaction.md`](./transaction.md)). `Global.serialize` of such a Box fails in both (`CSigmaDslBuilder.scala:264-269` → `DataSerializer.scala:16-18`; `EvalError('global-serialize-failed')`). Adversarial-only: an output's index is its position, below 32768.

For the body-only round-trip (i.e., parsing a `parseExpr` output and reserializing through `serializeExpr` into a fresh `ByteWriter`), the same byte-equality invariant holds.

## Type invariants (wire-side shapes)

These hold on every `ErgoTree` returned by the public API. Callers may rely on them without re-checking. The discriminated-union types `SValue`, `Expr`, and `SigmaBoolean` are shared across slices — see [`facts/ergoscript-eval.md`](./ergoscript-eval.md) for the canonical `SValue` / `SType` / `Expr` definitions and [`facts/ergoscript-sigma.md`](./ergoscript-sigma.md) for `SigmaBoolean`.

```ts
type Network = 'mainnet' | 'testnet'
type AddressType = 'P2PK' | 'P2S'

interface TreeHeader {
  version: 0 | 1 | 2 | 3 | 4 | 5 | 6 | 7   // bits 0..2 of rawHeader
  hasSize: boolean                          // bit 3: VLQ-u32 body size follows
  constantSegregation: boolean              // bit 4: segregated constants section
  rawHeader: number                         // the header byte as received: bits 0–4 match the three
                                            // fields above; bits 5–7 are kept as stored
}

interface ErgoTree {
  header: TreeHeader
  constantTypes: SType[]            // parallel to constants[]; required for byte-exact re-serialize
  constants: SValue[]               // empty when header.constantSegregation === false
  body: Expr                        // root expression
}
```

- `rawHeader` is the on-wire byte. The `version`, `hasSize`, `constantSegregation` fields are derived projections kept on the struct so callers don't need to re-decode bits. `serializeTree` writes `rawHeader` as stored and validates only its bits 0–4 against the derived fields — a hand-constructed `ErgoTree` whose bits 0–4 disagree is rejected at serialize time with `'header-inconsistent'`. Bits 5–7 round-trip: the JVM writes the header as stored and never inspects them (`ErgoTreeSerializer.scala:79-91`). The mainnet burn box's header `0xcd` has bits 6–7 set.
- `constantTypes` is parallel to `constants[]` and carries the per-constant `SType` recovered from the wire. It's necessary because a parsed `SValue` does not unambiguously encode its `SType` for some edge cases (empty `Coll`, `None` for `SOption`); sigma-rust avoids this because its `Constant { tpe, v }` couples them at the struct level.

`ErgoBox` and `AvlTreeData` shapes are stable. `Closure` remains forward-declared until the FuncValue/Apply evaluator arms land. Evaluator-only fields may still be added in later phases (see [`facts/ergoscript-eval.md`](./ergoscript-eval.md)).

```ts
interface ErgoBox {
  // ... value, ergoTree, creationHeight, tokens, txId, index ...
  registers: Record<number, { tpe: SType; value: SValue } | undefined>
}

interface AvlTreeData {
  digest: Uint8Array              // parse: exactly 33 bytes (fixed-33 read); runtime: any length (JVM accepts any)
  treeFlags: number               // u8: bit 0 insertAllowed, bit 1 updateAllowed, bit 2 removeAllowed, bits 3-7 reserved
  keyLength: number               // u32 (VLQ-encoded on the wire)
  valueLengthOpt: number | null   // null = variable; non-null = fixed value length
}
```

- `ErgoBox.registers` carries a per-register `SType` (the `{ tpe; value }` record), matching sigma-rust's `NonMandatoryRegisters` storing `Constant<'static>`. The per-register `SType` is required by the downstream `ExtractRegisterAs` evaluator arm's type-assertion (see eval slice).
- **GroupElement canonical-bytes invariant:** every GE value reaching the runtime is canonical — a curve-valid compressed point or the canonical 33-zero identity. The wire layer enforces this at parse (see `GroupElement canonical parse` below); the canonical home for the invariant is [`facts/ergoscript-eval.md`](./ergoscript-eval.md) Type invariants.

## Wire encoding by construct

The per-construct wire formats below complement the function signatures (Internal modules) and the error taxonomy (which lists each code's trigger). Where a code is named here, its enumeration lives in the taxonomy.

### `SUnsignedBigInt` value codec (type code 9)

`SUnsignedBigInt` is in the `SType` union as **type code 9** (`SEmbeddable`, `SNumericType`; JVM `SType.scala:547`). Handling is **permissive at the wire layer** — the v3 gate lives in the evaluator's `validateV6Types` pre-eval pass (see [`facts/ergoscript-eval.md`](./ergoscript-eval.md)), NOT here. This matches ergots' established pattern for `validateBinOpTypes` (parser stays permissive; consensus rejection is pre-eval).

- **`parseSType` / `serializeSType`:** embeddable type code 9 ↔ `{ tag: 'SUnsignedBigInt' }` (permissive; accepted at any tree version). The JVM gates code 9 via `embeddableV6` (selected by `isV3OrLaterErgoTreeVersion`); ergots accepts unconditionally for byte-roundtrip, and the pre-eval pass enforces the gate. `serializeSType` emits code 9 via the `embeddablePrimitiveCode` path AND the main `serializeSType` switch (so composite type-codes `Coll[UBI]`, `Option[UBI]`, tuple-containing UBI, and `SFunc`-containing UBI all work through the normal compact-form machinery).

The value codec is **distinct from `SBigInt`** (consensus-critical — different byte representations for the same numeric values):

| | `SBigInt` (existing) | `SUnsignedBigInt` |
|---|---|---|
| Encode | `toByteArray` — signed two's-complement, minimal; high-bit-set positive ⇒ leading `0x00` | `asUnsignedByteArray` — unsigned magnitude, minimal; no sign padding |
| Decode | `new BigInteger(bytes)` — signed | `fromUnsignedByteArray(bytes)` — unsigned magnitude |
| Range | `[-2^255, 2^255−1]` | `[0, 2^256−1]` |
| `0` encodes to | `[0x00]` (1 byte, VLQ len `01 00`) | `[]` (empty, VLQ len `00`) |
| `128` encodes to | `[0x00, 0x80]` (2 bytes) | `[0x80]` (1 byte) |

Length framing: VLQ `putUShort`/`getUShort` (Scorex `putUShort` is plain VLQ, so ergots' existing `writeVlqU`/`readVlqU` is correct). Source: `CoreDataSerializer.scala:39-42, 118-124`.

Confirmed edge cases (each a required test vector):

- **`0` → `[]` (empty; wire `00`).** `sigma.crypto.BigIntegers.asUnsignedByteArray(0)` strips the leading zero unconditionally (`BigIntegers.scala:110-118`). The loop `while (n > 0n) { unshift(n & 0xff); n >>= 8n }` never runs for `0n` → empty array. This is the **opposite of `SBigInt`** where `0 → [0x00]`.
- **No high-bit sign padding.** `128` → `[0x80]` (1 byte). The encoder MUST be a fresh magnitude encoder — NOT a tweak of `encodeBigIntBE` (whose `unshift(0x00)` high-bit pad must NOT carry over).
- **Length-0 on the wire decodes to `0n`** (`fromUnsignedByteArray([]) → 0`; `CoreDataSerializer.scala:118-124` does NOT reject size 0). ergots **must accept** length-0 → `0n`; rejecting is stricter than the JVM = fork. (Contrast `SBigInt`, which rejects length-0.)
- **Decode cap 32 bytes** (`> 32` ⇒ `SValueParseError('unsigned-bigint-too-large')`; `CoreDataSerializer.scala:120`).
- **Non-negative only.** The encoder guards `v < 0n` → throws (unsigned: no negatives); the decoder yields a non-negative bigint by construction.
- **Non-canonical leading-zero inputs** (e.g. `[0x00, 0x05]`) decode to `5n` and re-encode canonically as `[0x05]` — accepted but not byte-identical on a round-trip of that specific input. Do NOT assert byte-identity on non-canonical test vectors.

Helpers (paralleling `encodeBigIntBE`/`decodeBigIntBE`): `encodeUnsignedBigIntBE(v: bigint): Uint8Array` (`v < 0n` ⇒ throw; emit minimal unsigned BE magnitude bytes via `while (n > 0n)` loop, no high-bit pad; `0n` → `[]`); `decodeUnsignedBigIntBE(bytes: Uint8Array): bigint` (fold bytes as unsigned magnitude BE; `[]` → `0n`). Codes: `'unsigned-bigint-too-large'` (parse + defensive serialize), `'unsigned-bigint-negative'` (defensive serialize).

**`SFunc` type code 112 — pre-existing permissive parse.** `parseSType` accepts type code 112 (`SFunc`) unconditionally (no version gate). The JVM gates it on `isV3OrLaterErgoTreeVersion` (`TypeSerializer.scala:211`). This pre-existing over-accept is closed by the evaluator's `validateV6Types` pass (which deep-walks for `SFunc` everywhere it walks for `SUnsignedBigInt`) — the parser stays permissive for byte-roundtrip; consensus rejection is pre-eval.

### `AvlTreeData` value layout

The wire format mirrors sigma-rust `ergotree-ir/src/mir/avl_tree_data.rs:71-90`:

1. `digest` — **Parse:** ADDigest `scorex_parse` reads exactly 33 bytes (`read_exact(33)`; `ergo-chain-types/src/digest32.rs:149-153`). On-wire: 33 RAW bytes, NO length prefix. The 33rd byte is the tree-height byte. **Serialize:** the JVM `DataSerializer` writes `AvlTreeData.digest` verbatim via `putBytes` with no length requirement (`CAvlTree.scala:31-34` no-require); any runtime digest length is written as-is. An AvlTree SValue produced by `updateDigest` with a non-33-byte digest serializes fine but does NOT round-trip through parse — an intentional JVM asymmetry.
2. `treeFlags` — single `u8` via `put_u8`. Bits 3-7 round-trip identically (no masking). The JVM keeps only bits 0–2 (`AvlTreeFlags(r.getByte())`, `AvlTreeData.scala:21-26, 83`) and writes those back (`serializeFlags`, `:28-34, 74`), so a flags byte with bits 3–7 set re-serializes differently there: a documented residual ([`facts/transaction.md`](./transaction.md) Known residual 3), which reaches a transaction's signing message, and so its id and its output box ids, through an AvlTree value in an output's tree or registers, or in an input's context-extension values.
3. `keyLength` — **parse:** VLQ `u32` via `put_u32` (which is `put_u64(v as u64)` in `sigma-ser/src/vlq_encode.rs:78`; NOT fixed 4-byte big-endian), matching the JVM's `r.getUInt().toInt` (`AvlTreeData.scala:84`), which wraps a value in `[2^31, 2^32)` negative as an Int (the `SAvlTree.keyLength` i32 view, `facts/ergoscript-eval.md`). **Serialize (2026-09-28 controller ruling):** bounded to `[0, 2^31 - 1]` — was `[0, 2^32 - 1]`. The JVM holds `keyLength` as an `Int` and writes it with `putUInt` (`AvlTreeData.scala:77`), which rejects a negative `Int` (`"… is out of unsigned int range"`, pinned by `DeserializationResilience.scala:386-395`); a value parsed from `[2^31, 2^32)` can therefore be PARSED but not RE-ENCODED by the JVM, so ergots rejects it too. See Round-trip Carve-out 6.
4. `valueLengthOpt` — `Option<Box<u32>>` SigmaSerializable (`serialization/serializable.rs:212-231`): `Some(v)` = `0x01` tag + VLQ-u32 inner value; `None` = `0x00` tag. Parser is permissive — any non-zero tag byte is treated as `Some` (Carve-out 2). Serializer canonicalizes to `0x01` for `Some`, and bounds the inner value to `[0, 2^31 - 1]` for the same reason as `keyLength` (`AvlTreeData.scala:78, 85`; Carve-out 6).

Serialize codes: `'savltree-tree-flags-out-of-range'`, `'savltree-key-length-out-of-range'` (`keyLength` outside `[0, 2^31 - 1]`, 2026-09-28), `'savltree-value-length-out-of-range'` (`valueLengthOpt`'s inner value outside `[0, 2^31 - 1]`, 2026-09-28). The parser delegates length / VLQ-overflow checks to `ByteReader` (no AvlTree-specific parse codes).

### `CreateAvlTree` operand layout

**Source: JVM `CreateAvlTreeSerializer.scala:24-37` + `trees.scala:79-91`.** The JVM serializes `CreateAvlTree` (opcode `0xb6`) as FOUR expr operands, all through the expr channel (`w.putValue(...)` ×4 / `r.getValue()` ×4):

```
[flags: Expr]            -- type SByte
[digest: Expr]           -- type SColl(SByte)
[keyLength: Expr]        -- type SInt
[valueLengthOpt: Expr]   -- type SOption(SInt)
```

The 4th operand is an expr whose *type* is Option (`valueLengthOpt: Value[SIntOption]`, `trees.scala:82`) — "no value length" is an Option-typed expr evaluating to None (the compiler emits `Const(SOption[SInt], None)`), NOT an absent operand. No presence tag anywhere in the run.

**sigma-rust forks this layout** (`ergotree-ir/src/mir/create_avl_tree.rs`): its 4th operand is `Option<Box<Expr>>` — a one-byte presence tag (`0x00` absent / `0x01` expr follows). The two shapes are mutually unparseable: JVM-emitted bytes put an expr lead byte (e.g. ConstantPlaceholder `0x73`) where sigma-rust expects the tag, and sigma-rust-emitted bytes put a tag byte where the JVM expects an expr. ergots originally ported the sigma-rust shape; the fork is now fixed to the JVM layout and routed to sigma-rust. Consequences:

- MIR `CreateAvlTree.valueLength` is `Expr` (not `Expr | null`) — always present, Option-typed (`mir/types.ts`).
- `wire/mir/create-avl-tree.ts` parse/serialize: four `parseExpr`/`serializeExpr` calls, no tag byte. Blessed-vector tree bytes round-trip byte-identically (pinned in `test/wire/avl.test.ts`).
- Eval-tier: both `CreateAvlTree` and `TreeLookup` reject unconditionally (`'unsupported-eval-node'` — the JVM has no eval override for either); see [`facts/ergoscript-eval.md`](./ergoscript-eval.md). Parse stays — the JVM parses both nodes fine.

### `ValDef` / `FunDef` (opcodes `0xd6` / `0xd7`)

`OP_FUN_DEF` (`0xd7`, 215) is **parsed**. A `FunDef` is a polymorphic `let f[T] = rhs` — a `ValDef` with a non-empty list of type parameters. The JVM treats it as a `ValDef` whose `companion` switches to `FunDef` exactly when `tpeArgs` is non-empty; ergots mirrors this on the same `ValDef` MIR node rather than introducing a new variant:

```ts
interface ValDef {
  tag: 'ValDef'
  id: number
  rhs: Expr
  tpeArgs?: STypeVar[]   // absent or empty ⇒ plain ValDef, non-empty ⇒ FunDef
}
```

The MIR `tag` stays `'ValDef'` for both shapes; the opcode is chosen from `tpeArgs.length` at serialize time (matching the JVM `companion`).

**Wire encoding.** `FunDef` shares the `ValDef` body prefix with a type-arg list inserted before `rhs`:

1. `id` — VLQ-u32 (same as `ValDef`).
2. **`FunDef` only:** `nTpeArgs` — a **raw `u8`** (NOT VLQ; a single byte read directly). The JVM reads it via **signed** `getByte()` then `safeNewArray[STypeVar](nTpeArgs)`, which throws on a negative size, so a count `>= 128` is rejected; ergots mirrors this with `ExprParseError('fun-def-tpe-args-out-of-range')` for `nTpeArgs > 127` (`ValDefSerializer.scala:38`). Then `nTpeArgs` × `SType` via `parseSType` (which already parses `STypeVar` at type code 103). **Each parsed type-arg MUST be an `STypeVar`** — a non-`STypeVar` raises `ExprParseError('fun-def-tpe-arg-not-type-var')`.
3. `rhs` — Expr via the existing `getValue` path.

A plain `ValDef` (opcode `0xd6`) carries no `nTpeArgs`/type-arg list — `id` is followed directly by `rhs`. Both shapes populate the shared scope-wide `valDefTypes` map with `rhs.tpe`, so a downstream `ValUse` resolves identically regardless of `tpeArgs`. **Serialize** chooses the opcode from `tpeArgs.length`: non-empty → `0xd7` (emit `id`, then `nTpeArgs` as a raw `u8` — rejected with `ExprSerializeError('fun-def-tpe-args-out-of-range')` for `length > 127`, mirroring the JVM `w.put(len.toByteExact)` which is Byte-exact (`ValDefSerializer.scala:20`); note this serialize cap is **127**, unlike `Tuple` whose serialize uses `putUByte` and caps at 255 — then each `STypeVar` via `serializeSType`, then `rhs`); empty → `0xd6` (the pre-existing plain-`ValDef` path, byte-identical to before). **Byte-roundtrip is load-bearing** — `serializeExpr(parseExpr(b))` is byte-equal for every `FunDef`-containing body.

`FunDef` itself is parsed/serialized at **every** tree version (the opcode and `STypeVar` type code carry no version gate, matching the JVM). An `SFunc` type code (112) *appearing inside* a `FunDef`'s `rhs` or its type-arg list stays caught by the evaluator's `validateV6Types` `SFunc`-type-code gate under `treeVersion < 3` (see [`facts/ergoscript-eval.md`](./ergoscript-eval.md)) — no new wire-layer gate.

### `STypeVar` name — length + UTF-8 decode (type code 103)

`STypeVar` encodes as `[103][u8 name length][UTF-8 name bytes]`. The JVM (`TypeSerializer.deserialize:203`) reads the length via **`getUByte()`** (unsigned, 0..=255) with **no bound** and builds `STypeVar(new String(getBytes(len)))` — so name length 0 yields `STypeVar("")` and 255 is accepted. ergots matches: parse accepts 0..=255 (truncation past the buffer is still caught by `readBytes`); serialize rejects only `> 255` UTF-8 bytes (`STypeSerializeError('stypevar-name-length')`) — what the u8 length field cannot hold, and what the JVM's `putUByte` refuses too. A name of ill-formed bytes can decode to one whose re-encoding is longer than 255 bytes (the lossy decode below): such a tree parses but cannot be written (Round-trip Carve-out 7). The earlier `[1, 254]` bound mirrored sigma-rust's `BoundedVec<1, 254>` and was a JVM fork in BOTH directions (over-rejecting 0 and 255); the parse code `'invalid-stypevar-length'` is retired (see Retired codes). Reachable via `FunDef` type-args and `SFunc` type params; adversarial-only.

**UTF-8 decode is JVM-faithful lossy, never rejecting.** The JVM's `new String(bytes, UTF_8)` lossy-decodes ill-formed UTF-8 to U+FFFD (it never throws), so ergots decodes the name bytes via `decodeUtf8Lossy` (`wire/_utf8.ts`) — a port of Java's `sun.nio.cs.UTF_8.Decoder` malformed-length rule — rather than strict-rejecting. The byte sequence where this matters is an ill-formed UTF-16 surrogate (`ed a0 80`): the JVM collapses the whole 3-byte unit to a **single** U+FFFD, whereas WHATWG / Rust `from_utf8_lossy` (and a naive `TextDecoder`) emit **three** — a different re-encoded name → a different `ErgoTree` template → a wire round-trip fork. `serializeSType` re-encodes the decoded name from structure (`TextEncoder`), so a non-canonical name round-trips to the JVM-canonical bytes. Pinned by the SANTA-blessed vector `STypeVar.name_utf8_roundtrip` (5 entries, `jvm:sigma-state-6.0.3`, vendored at `test/fixtures/conformance/wire/`); the per-byte JVM table is in `test/wire/utf8-lossy.test.ts`. The earlier strict-reject code `'invalid-stypevar-utf8'` is retired (see Retired codes). Adversarial-only — honest tools never emit a malformed type-var name.

### `SString` data — UTF-8 decode

`SString` data is a VLQ `u32` length and that many bytes, which the JVM decodes with `new String(bytes, UTF_8)` (sigma-state v6.0.6 `CoreDataSerializer.scala:104-110`). ergots decodes them with the same `decodeUtf8Lossy` as `STypeVar` names, never `TextDecoder`, which differs from Java in two ways. `TextDecoder` strips a leading byte-order mark, where Java keeps `EF BB BF` as U+FEFF. And it decodes an ill-formed surrogate `ED A0 80` to three U+FFFD, where Java gives one. Either difference changes the decoded value: a String register or context-extension value that the JVM tells apart would compare equal, or re-serialize to different bytes. Serialize re-encodes the string as UTF-8, so a string decoded from ill-formed bytes re-serializes with `EF BF BD` in place of each malformed unit, as the JVM's `getBytes(UTF_8)` does.

### Explicit type arguments (MethodCall / PropertyCall)

**Source: JVM `PropertyCallSerializer.scala:20-49` (byte-identical to `MethodCallSerializer`'s explicit-type-arg tail).** Some methods carry explicit type arguments on the wire after the method body. The shared registry `explicitTypeArgNames(typeId, methodId): readonly string[]` (`wire/mir/explicit-type-args.ts`) drives both serializers: after writing the method body, the serializer iterates the registered type-parameter names and writes one `SType` per name via `putType(typeSubst(a))`; the parser reads the same count of `SType` values. Trees with no registered names for a `(typeId, methodId)` consume/emit no extra type bytes (backward-compatible).

Both `MethodCall` and `PropertyCall` MIR nodes carry an `explicitTypeArgs: Record<string, SType>` field (empty `{}` for nodes with no registered names; byte-roundtrip unchanged):

```ts
interface PropertyCall {
  tag: 'PropertyCall'
  obj: Expr
  typeId: number
  methodId: number
```

### `GroupElement` canonical parse

Every wire ingress that reads a 33-byte GE payload applies **validate + normalize** (establishing the GE canonical-bytes invariant; canonical home `facts/ergoscript-eval.md` Type invariants):

- **0x00-lead** (any bytes 1..32) → NORMALIZE to the canonical 33-zero identity. Mirrors JVM `GroupElementSerializer.parse` (`core/.../GroupElementSerializer.scala:35-42`): any 0x00-lead encoding reads into the identity POINT (payload tail discarded); every JVM egress re-serializes canonically (`:20-33`). Same semantics the lenient `decodePoint` already ships on the eval `DecodePoint` arm.
- **non-0x00-lead** → must curve-decode (secp256k1 SEC1 compressed): bad prefix or x-not-on-curve throws (`'group-element-invalid-point'` at the SValue arm, `'ec-point-invalid'` at SigmaBoolean leaves). The JVM rejects at the same layer — all tree versions, dead branches included.
- **Ingress coverage:** the SValue GE data arm (body + segregated constants, box registers via `parseAdditionalRegisters`, `deserializeTo[GroupElement]`); SigmaBoolean leaf points (ProveDlog.h, ProveDHTuple g/h/u/v — `wire/sigma-boolean.ts`); the `deserializeTo[Header]` hydration leg (minerPk + v1 powOnetimePk — the JVM parses both through `GroupElementSerializer.parse`, AutolykosSolution serializers, `ErgoHeader.scala:157-180`). The eval `DecodePoint` arm is already conformant (decodes, then re-encodes canonically).
- Curve validation reuses the existing `crypto/secp256k1.ts` `decodePoint` adapter (`@noble/curves` — already a dependency of this package; no new dependency).
- Round-trip consequence: Carve-out 3 (§Round-trip invariant). Serialize side is unchanged — canonical values serialize verbatim, and the invariant guarantees canonicality.

### `SBox` candidate-size window (4096 bytes)

**Source: JVM `ErgoBoxCandidate.scala:144,191-235` + `ErgoBox.scala:214-225` + `SigmaConstants.scala:24` + `CoreByteReader.scala:25-27,36-108,133-137` + `ValidationRules.scala:169-189`; LAZY semantics empirically pinned (blessed `jvm:sigma-state-6.0.3`).**

ergots' SBox data parse previously rejected token count > 122 (`'sbox-tokens-out-of-range'`), mirroring sigma-rust's `BoundedVec<Token, 1, 122>` data-layer cap (their own comment, `ergo_box.rs:100-104`, marks it a count-shaped approximation of the size rule; `MAX_BOX_SIZE` binds tx-level only there). The JVM data layer has **no token-count rule at all**:

- `ErgoBoxCandidate.serializer.parseBodyWithIndexedDigests` reads `nTokens = r.getUByte()` bare (`ErgoBoxCandidate.scala:200`) — the u8 read's natural ceiling 255 is the only count bound. `SigmaConstants.MaxTokens` (255) binds ONLY in SDK builders (`OutBoxBuilder.scala:34`, `JavaHelpers.scala:369`) — unreachable from parse/eval.
- The real gate is a **4096-byte candidate-size window**: `r.positionLimit = r.position + ErgoBox.MaxBoxSize` (4096, `SigmaConstants.scala:24`) at candidate start (`ErgoBoxCandidate.scala:191-192`), restored at `:235`. The window covers the candidate span value→registers; `txId`/`index` sit OUTSIDE it (`ErgoBox.scala:214-225`). Crossing throws `CheckPositionLimit` = validation rule 1014 (`ValidationRules.scala:169-189`).

**LAZY window semantics:** the JVM checks `position > positionLimit` BEFORE each logical primitive read (`CoreByteReader.scala:25-27`; per-get call sites `:36-108`) — ONE check per logical read (`getULong` = one check, then its VLQ continuation bytes read unchecked; `getBytes` = one check, then N bytes). Consequences:

1. A read whose START is ≤ the limit may END past it (straddle tolerated).
2. An overrun by the candidate's FINAL read ESCAPES entirely — e.g. 2 tokens + a trailing 4200-byte R4 register, candidate 4281 B > 4096 → the JVM ACCEPTS. A small R5 register AFTER the fat R4 errors, because R5's read begins past the limit.
3. A read beginning exactly AT the limit passes (the check is strict `>`).

**Measured boundary** (minimal candidates): 122 tokens = 4038 B; 123 tokens = 4071 B (fits → the JVM accepts — the old 122 cap was not even the right count approximation); 124 tokens = 4104 B (cannot fit → always rejects via rule 1014).

**Nested-window widening:** the JVM `positionLimit_=` is a PLAIN assignment with NO clamp (`CoreByteReader.scala:133-137`), so a nested window (a box constant inside a register of an outer box, or a tree's own 4096-byte window, set at the tree's start inside its box's window; see `parseTreeFromReader`) may legitimately EXCEED the outer limit for the inner span; the save/restore discipline reinstates the outer limit afterward. The scorex facility mirrors this exactly — canonical contract in [`facts/scorex.md`](./scorex.md) (positionLimit window block).

ergots implementation:

- `@ergots/scorex`'s `ByteReader` gains the `positionLimit` facility: getter + setter (plain assignment, no clamp), default = buffer byte length; entry check at the start of each logical consuming primitive (`readU8`, `readBytes`, `readVlqBigInt`; the other read helpers inherit) → `ReaderError('position-limit-exceeded')`. Every window is armed on the one shared reader, as the JVM's are: this candidate window, and each tree's own window (`MAX_PROPOSITION_SIZE`). Since 2026-09-28 ergoscript forks no sub-readers; the JVM never forks. See [`facts/scorex.md`](./scorex.md).
- The SBox data-parse arm (`parse-svalue.ts`) saves the prior limit, sets `r.position + 4096` at candidate start (before the value read), and restores INLINE after the registers loop and before the txId read — mirroring `:191`/`:235`. No try/finally, as in the JVM: a throw leaves the candidate limit in place, and a sized tree that degrades on it restores its own saved limit in its `finally`, as the JVM's tree parse does (`ErgoTreeSerializer.scala:210-212`). Applies wherever SBox DATA parses (body/segregated constants, box registers, `deserializeTo[Box]`).
- The >122 parse count-gate is DELETED — no token-count check remains at parse (u8 is the natural ceiling). Window overruns surface as scorex `ReaderError('position-limit-exceeded')`, so SBox parse can throw `ReaderError`, not only `SValueParseError`. Inside a tree (a Box constant) the overrun is rule 1014, in the degrade set: it degrades a sized enclosing tree and is wrapped as `'soft-fork-without-size-bit'` by an unsized one; it surfaces as `ReaderError` only from a window outside any tree.
- `serialize-svalue.ts` KEEPS `'sbox-tokens-out-of-range'` but relaxed to threshold > 255 (u8 ceiling): mirrors the JVM egress `putUByte(size)` (`ErgoBoxCandidate.scala:144`; scorex-util `putUByte` asserts 0..255). The JVM applies NO size window on egress — the 4096 window is a parse-only rule.

**Conformance families:** `Box.token_window_const.json` / `Global.deserializeTo_Box_token_window.json` (blessed `jvm:sigma-state-6.0.3`) — covering the 123-token accept, 124-token reject, fat-trailing escape-accept, and fat-then-reg reject shapes.

**sigma-rust divergence (BOTH directions; ergots leads, routed to sigma-rust):** sigma-rust rejects 123–255-token candidates the JVM accepts (count cap tighter than the real rule) AND accepts candidates whose non-final reads begin past 4096 that the JVM rejects (no window at the box data layer). Both directions are consensus-relevant on adversarial bytes; mainnet-honest boxes sit far inside both bounds.

## Known residuals of the tree parse (spec 2026-09-28)

Numbered as in the "Residuals" section of `docs/specs/2026-09-28-sized-tree-declared-size-design.md`; this file cites them as "residual N". Each is a documented divergence from the JVM, not closed. All but residual 11 are adversarial-only: honest trees declare their true size, have SigmaProp roots and, written as the JVM writes them, re-encode to themselves.

1. **The method catalog.** `exprTpe` knows the result type of about 76 `(typeId, methodId)` pairs (28 explicit, 48 numeric; `mir/method-signatures.ts`), and the parser accepts any pair (`wire/mir/property-call.ts:59-74`). An unregistered pair types as ergots' own `SAny`, which rule 1001 passes, so it passes a root whose type falls back to that `SAny` — for example `00 db 65 01 fe`, whose root is `CONTEXT.dataInputs` — where the JVM, which knows the method's type, fails the rule. The same holds wherever else the method typing makes its own `SAny`:
   - `resolveReturnTpe`'s fallback (`mir/method-signatures.ts:303`), a fresh `SAny` for a result type variable left unbound. That includes a variable bound to a wire-declared type variable, as in `0b 0a dc 6a 04 dd 01 0e 00 67 01 58` (`Global.deserializeTo[X]` with `X` an `STypeVar`), which the JVM types `STypeVar(X)` (`sigma/ast/values.scala:1355-1357`) and fails; the catalog follow-up does not close this case, since `106:4`'s signature already matches the JVM's. It also includes operand types that conflict, as in `0b 09 dc 04 09 d4 61 01 01 04 00` (`Int.bitwiseOr` on a `DeserializeContext(SAny)` receiver, whose type variable meets both that `SAny` and `SInt`), where the JVM specializes the method to its owner type (`sigma/ast/methods.scala:235-257`) and fails the `SInt` root.
   - A type variable bound to a tuple's element type (`unifyTypes`' collection-against-tuple case; the JVM binds it to `SAny` too, `core/.../sigma/ast/package.scala:46-47`, and fails such a root).

   The JVM's `SAny` (type code 97, or a tuple's element type) fails the rule, as in the JVM, when it reaches the root through `exprTpe`'s own arms (see "Rule 1001 on the box paths"); `unifyTypes`' element type for a tuple is that same `SAny` in the JVM, and marking it `SANY_JVM` would close the second case above. Where the method typing replaces it with one of ergots' own, it passes: `00 db 24 03 e3 01 61`, `SOption.get` on `GetVar(1, SAny)`, whose pair the catalog lacks, parses under `checkType`. For an unsized tree ergots accepts a box the JVM rejects. A sized tree the JVM degrades, so its spend rejects, where ergots parses it and evaluates a spend; with a wrong declared size the two also continue the box at different bytes. A follow-up spec transcribes the JVM's v5 and v6 method catalog, which also closes B-full's unknown-method gate (residual 3), though not the fallback cases above.
2. **The v5+ tree-version check.** The JVM rejects a tree whose version exceeds the activated script version (checked since v5, `core/.../sigma/VersionContext.scala:17-21`; the inner catch turns the `IllegalArgumentException` into a `SerializerException`, `ErgoTreeSerializer.scala:191-193`). The wire layer has no activated version, so such a tree parses or degrades in ergots where the JVM rejects it.
3. **B-full.** Unknown type codes, method gates and rule 1009 for SFunc data (SANTA `4ac2286`) degrade a sized tree in the JVM and reject in ergots. This includes the UnsignedBigInt type code in a pre-v3 tree, which the JVM's type table rejects while reading the type and ergots accepts, so a malformed UnsignedBigInt register in a pre-v3 tree rejects in ergots where the JVM degrades. See `docs/specs/2026-06-17-ergotree-unparsed-soft-fork-preservation.md` §"B-full residual".
4. **Registers.** Tuple-expression registers keep their received bytes (`opaqueBytes`), and AvlTree flags stay unmasked (`facts/transaction.md` Known residual 3). The JVM also accepts ConcreteCollection and GroupGenerator register values (rule 1019's arms, `org/ergoplatform/validation/ValidationRules.scala:188-193`), where ergots accepts only constants and tuples. A register Tuple's items are held to the same two forms, where the JVM reads each item with `r.getValue()` (`TupleSerializer.scala:32-34`) and casts only the `Tuple` node itself to an evaluated value (`sigma/ast/values.scala:807-809`); and a register Tuple of arity 0 or 1, which the JVM parses, rejects in ergots (`'sbox-register-tuple-arity'`). Register values the JVM cannot re-encode belong here too, for example an AvlTree register whose `keyLength` is 2^31 or more (Carve-out 6's shape, in a register) or one of a 1-item tuple type (Carve-out 1's): they parse in both, and the JVM rejects a transaction whose output carries one at parse, since its eager id writes the registers from their structure (`ErgoBoxCandidate.scala:175`; ergo-core `ErgoTransaction.scala:68`), where ergots rejects it only when it computes the id or re-serializes the box ([`facts/transaction.md`](./transaction.md), `parseTransaction`); a Box value whose index is 0x8000 or more is one (Carve-out 9). The lead byte of a register value or a register Tuple's item follows the JVM's rule 1002 only in part (2026-09-29): an opcode with no JVM serializer is soft, as `parseExpr` classifies it (see `parseAdditionalRegisters`), but ergots rejects every other opcode on its lead byte, where the JVM parses the node's payload before it casts the node (`ErgoBoxCandidate.scala:231`). So a known opcode whose payload holds a soft failure degrades an enclosing sized tree in the JVM and rejects in ergots (`d1 84` as a nested box's R4), and a known opcode as a Tuple item, which the JVM does not cast, parses in the JVM (`86 02 04 00 a3`; both from a sigma-state 6.0.6 probe). The JVM also writes a ConcreteCollection register of Boolean constants back as `0x85` (Carve-out 8), which ergots, rejecting such registers, never writes. Register re-encoding and grammar wait for SANTA's answers to follow-ups 6–7.
5. **The constant-store leak, and the six opcodes.** A JVM tree installs its constants as the reader's constant store and restores the previous store only on success (`ErgoTreeSerializer.scala:156-158, 177`), so after a degrade the degraded tree's store stays on the reader; ergots keeps no reader-wide store and does not follow it. And ergots degrades on six opcodes the JVM parses (the `'opcode-reserved'` entry in the error taxonomy; `OPCODES_THE_JVM_PARSES`). As a register's lead byte they stay hard rejects (2026-09-29): the JVM has a serializer for each, so its rule 1002 does not apply to them. The JVM parses TaggedVariable and the three ModQ opcodes there and then rejects them at the register's cast, as ergots does, unless their payload holds a soft failure first, which degrades an enclosing sized tree in the JVM (`e7 84` as a nested box's R4); it accepts TrueLeaf and FalseLeaf as Boolean-constant registers, written back as `01 01` / `01 00`, where ergots rejects them. Classifying them as `parseExpr` does would have degraded the enclosing tree for all six, turning four JVM rejects into accepts.
6. **`parseTree`'s envelope, including P2S address decoding.** The 1 MiB `'oversized'` cap, and the `'trailing-bytes'` reject beyond a sized tree's declared span (ERG-02). The JVM's lenient parse ignores trailing bytes, and degrades or parses a sized tree above 1 MiB, which ergots rejects as `'oversized'`: a read that begins past the 4096-byte window degrades it (unless it is a value read at the very end of the input; see "Value read order"), and a tree whose last read straddles the window parses (`SString` data, for one, is a single `getBytes` after a `getUIntExact` length, `CoreDataSerializer.scala:104-110`; `startReader` has no size cap, `SigmaSerializer.scala:22-33`). In both cases the JVM accepts the sized tree; an unsized one above 1 MiB it accepts only in the straddling case. This touches only the ErgoTree kind and address decoding: box trees are bounded by the 4096-byte windows.
7. **Block context.** ergo-core parses all of a block's transactions on one reader (`ergo-core/.../modifiers/history/BlockTransactions.scala:184-195`). When a tree's next read is a value read that begins past its window at the very end of its transaction, the JVM's verdict therefore depends on what follows: with another transaction after it, the first-byte peek sees a real byte and the window check then degrades the tree; parsed on its own, the peek hits the end and the transaction rejects. ergots parses each transaction on its own and takes the standalone verdict. The residual is this case only: a data read past the window meets the window check first and degrades the tree in both settings, and a read inside the window reads on, in the block, into the next transaction. SANTA's BlockTransactions kind (`02c60db`) pins the block side.
8. **A ValDef whose right-hand side is `Apply` of a non-function, non-collection.** The JVM types it `NoType` and parses on; ergots rejects with `'val-def-rhs-tpe'`, since its ValDef parse needs the type. This predates the change; only the collection case is fixed.
9. **Collection item types.** The JVM asserts that each ConcreteCollection item has the declared element type (`ConcreteCollectionSerializer.scala:38`); ergots does not check, so it accepts what the JVM rejects. This predates the change.
10. **The ValDef type store.** The JVM keeps one store per reader (`SigmaByteReader.scala:32`), so the outputs of one transaction share it: a ValDef in output 0's tree resolves a ValUse in output 1's (SANTA `02c60db`, `Transaction.valdef_scope#0`, accepted). ergots starts a fresh map for every tree, so it rejects that transaction. Adopting the reader's store needs its own look — the JVM's store is flat, while ergots may scope ValDefs inside one tree — and goes to a follow-up.
11. **The pre-v3 builder's arithmetic rewrites (2026-09-29).** The JVM parses a tree of version 0–2 with `DeserializationSigmaBuilder`, whose `applyUpcast` inserts an `Upcast` for the narrower of two numeric operands of different types in a comparison or an arithmetic node (`SigmaBuilder.scala:674-712`; not from v3 on, `:750-764`), and `ByIndexSerializer` upcasts a pre-v3 index to `SInt` (`ByIndexSerializer.scala:29-33`). Its writer in turn drops the `Upcast` of a constant in a pre-v3 tree (`serializable`, `ValueSerializer.scala:157-169, 362-373`). So the JVM re-encodes such trees differently from their bytes, where ergots writes them back as read (sigma-state 6.0.6 probe):
    - `00 d1 91 a3 05 00` (`HEIGHT > 0L`) → `00 d1 91 7e a3 05 05 00`;
    - `00 d1 91 7e 04 00 05 05 00` (`Upcast(0, Long) > 0L`) → `00 d1 91 04 00 05 00`;
    - `10 02 04 00 05 00 d1 91 73 00 73 01` (an Int placeholder above a Long one) → `10 02 04 00 05 00 d1 91 7e 73 00 05 73 01`: a placeholder is not a constant, so its `Upcast` stays;
    - `00 d1 91 9a a3 05 02 05 00` (`HEIGHT + 1L > 0L`) → `00 d1 91 9a 7e a3 05 05 02 05 00`;
    - `00 d1 b2 0d 01 01 7d a3 02 00` (`Coll(true)(HEIGHT.toByte)`) → `00 d1 b2 0d 01 01 7e 7d a3 02 04 00`.

    The transaction id, the output ids, `Global.serialize` and the serialize cost follow the re-encoding, so they diverge for such a tree. The same `upcastTo` rejects a pre-v3 index wider than an Int at parse (`00 d1 b2 0d 01 01 05 00 00`, an `AssertionError`), which ergots accepts: one of the node-construction checks the spec's follow-ups list. Modelling the rewrites needs `exprTpe` to type arithmetic as the builder does (the `Plus(Int, Long)` follow-up: ergots types it `SInt`, the JVM `SLong`), a broad change of its own. A JVM-compiled tree is already written as the builder leaves it, and so are the chain's served bytes; a tree from another encoder may not be. SANTA vectors for these shapes are a handoff request.
12. **The spend-time substitution (2026-09-29).** The JVM substitutes `DeserializeContext` and `DeserializeRegister` inside Kiama's `strategy`, which catches a `ClassCastException` and leaves the node in place (`core/.../sigma/kiama/rewriting/Rewriter.scala:180-190`). It takes a register's default untyped, and rebuilds the ancestors with their constructors but without `check2`. ergots types the decoded script and the default, throws on a register that is not `Coll[Byte]`, and runs `validateBinOpTypes` on the substituted body. The result is divergence in both directions, including six spends that the JVM and master accept and this branch rejects. See [`facts/ergoscript-eval.md`](./ergoscript-eval.md) "Deserialize family" and the spec's residual 12. It closes with the node-construction spec.

## Error taxonomy (wire-layer error classes)

Every wire-layer error class carries a `code: string` matching one of a fixed set of structural reasons for programmatic dispatch. `.message` is human-readable.

**Root-exported for `instanceof` classification:** the wire parse/serialize error classes — `ErgoTreeParseError`/`ErgoTreeSerializeError`, `ExprParseError`/`ExprSerializeError`, `STypeParseError`/`STypeSerializeError`, `SValueParseError`/`SValueSerializeError`, `SigmaBooleanParseError`/`SigmaBooleanSerializeError` — are all re-exported from the `@ergots/ergoscript` package root. They escape the boundary UNWRAPPED — a caller sees the typed failure from the innermost rejecting layer — with two exceptions in the tree parse (2026-09-28), each carrying the original error as `cause`: a soft-forkable failure in a tree without the size flag surfaces as `ErgoTreeParseError('soft-fork-without-size-bit')`, and a nested tree's run-out (a `'truncated'` escaping a nested tree, or a nested tree's degrade span past the end of the input) as `ErgoTreeParseError('nested-tree-truncated')`. A downstream consumer that classifies ergots failures by type can `import` and `instanceof` them. The mir-layer type-inference error `ExprTpeError` is root-exported too, since 2026-09-28: rule 1001 lets it escape a box-rules parse as a hard reject (see "Rule 1001 on the box paths"). scorex's `ReaderError` is owned by `@ergots/scorex` and is not part of this root-export guarantee.

```ts
class ErgoTreeParseError      extends Error { code: string; cause?: unknown }   // cause: the standard Error.cause
class ErgoTreeSerializeError  extends Error { code: string }
class ExprParseError          extends Error { code: string }
class ExprSerializeError      extends Error { code: string }
class STypeParseError         extends Error { code: string }
class STypeSerializeError     extends Error { code: string }
class SValueParseError        extends Error { code: string }
class SValueSerializeError    extends Error { code: string }
class SigmaBooleanParseError  extends Error { code: string }
class SigmaBooleanSerializeError extends Error { code: string }
class ExprTpeError            extends Error { code: string }
class ReaderError             extends Error { code: string }
class AddressDecodeError      extends Error { code: string }
```

- **`'sigma-boolean-empty'`** (`SValueSerializeError`) — retired at phase 2g-medium (`c00f835`). It guarded an empty raw `SigmaBoolean` byte form; a SigmaProp value is now the structural `SigmaBoolean` union, written by `serializeSigmaBoolean`, where an empty conjecture is `SigmaBooleanSerializeError('arity-out-of-range')`.
- **`'apply-func-not-sfunc'`** (`ExprTpeError`) — retired 2026-09-28. The `Apply` arm of `exprTpe` now follows the JVM's `Apply.tpe` (`sigma/ast/values.scala:1247-1251`): a collection function gives its element type, and any other function type that is neither `SFunc` nor `SAny` throws `'apply-func-no-type'` (the JVM's `NoType`), which took over this code's only site.

- **`'invalid-option-tag'`** — retired. Any nonzero wire Option tag now parses as Some (JVM scorex-util `getOption`; sigma-rust's `get_option` `1 => Some, _ => None` was a FORK on tags ≥ 2, no longer mirrored). Its last two sites were `DeserializeRegister.default` (now JVM `DeserializeRegisterSerializer.scala:30` `r.getOption(r.getValue())`) and the `CreateAvlTree` 4th operand (now an Option-typed expr, no tag). See Carve-out 2.
- **`'invalid-tuple-length'`** — retired. The generic-tuple TYPE parse arm mirrors JVM `TypeSerializer.scala:188-194` (`getUByte` + bare `STuple(items)`, no arity require), so arity-0/1 generic-tuple TYPES parse; the TYPE serializer keeps rejecting < 2 (`'tuple-too-short'`, `TypeSerializer.scala:93-94` `sys.error`) — parse/serialize asymmetric on the JVM itself. See Carve-out 1.
- **`'savltree-digest-length'`** — retired. The serializer writes the digest verbatim at any length — the JVM `DataSerializer` has no length require; parse-side remains fixed-33 (a JVM asymmetry). An AvlTree SValue with non-33-byte digest serializes fine but does NOT round-trip through parse.
- **`'sbox-ergo-tree-no-size'`** — removed. `parseSValue(SBox)` handles v0+hasSize=false ErgoTrees via `parseErgoTreeBytes` → `parseTreeFromReader` (the body Expr grammar is self-delimiting); the rejection was an incorrect assumption — ~99% of mainnet boxes use v0 P2PK trees without a size prefix.
- **`'invalid-stypevar-length'`** — retired. The `STypeVar` name-length parse mirrored sigma-rust's `BoundedVec<1, 254>` and rejected name lengths 0 and 255; the JVM (`TypeSerializer.deserialize:203`) reads the length via unbounded `getUByte()` and accepts 0..=255, so the bound was a fork in both directions (over-rejecting 0 and 255). Parse now accepts 0..=255 (truncation still caught by `readBytes`); serialize keeps `'stypevar-name-length'` for `> 255` only. See `STypeVar name — length + UTF-8 decode` above.
- **`'invalid-stypevar-utf8'`** — retired. The `STypeVar` name-bytes parse used a strict `TextDecoder({fatal:true})` that THREW on ill-formed UTF-8; the JVM (`TypeSerializer.deserialize:203`, `new String(bytes, UTF_8)`) lossy-decodes to U+FFFD and never rejects. Parse now uses `decodeUtf8Lossy` (Java `new String` collapse counts, incl. the `ed a0 80` surrogate → 1 U+FFFD vs WHATWG/Rust 3); no parse-side reject remains, and `serializeSType`'s `'stypevar-name-length'` (`> 255` bytes) is the only remaining STypeVar-name serialize reject. See `STypeVar name — length + UTF-8 decode` above + the SANTA `STypeVar.name_utf8_roundtrip` vector.

## Coverage

100% of MIR variants parse and serialize byte-identically against the PR 862 corpora (45 legacy + 14 ecosystem + 9 sig-15 = 68 trees), plus mainnet boxes (12,712 from the wider corpus + 173 from the original C2 corpus). Corpus round-trip test: 255 passing fixtures + 1 mainnet stub + 6 `known_unstable` (sigma-rust itself does not round-trip them).

The parse-mutation suite exercises 6,221 single-byte mutations: 66% throw a typed error class, 0 throw an untyped error, 100% taxonomy coverage (every wire-layer error class above is hit at least once).
